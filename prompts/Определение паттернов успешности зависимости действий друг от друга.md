# Определение паттернов успешности зависимости действий друг от друга

## Запрос

Допустим я доделал полную лингвистическую обработку в своём проекте "Карта Знаний". Все лингвистические признаки каждого лингвистического уровня передаются в модуль "Ядро Карты Знаний" или `knowledge_map_core`, это будет "лингвистический граф" (по сути JSON со всеми словами и всеми их свойствами, которые также оставляются в этом же JSON данные о смысле, а также связи между словами и связи между смыслами) который будет подаваться на вход.

Каким кодом можно будет находить паттерны зависимостей действий друг от друга которые успешно или не успешно ведут к достижению конкретной цели? То есть нужно как то сначала выявить эти паттерны из лингвистического графа модулем `knowledge_map_core`, а затем рассчитать успешные и не успешные шаги движения к цели.

## Ответ

Ниже — практическое, готовое к использованию руководство с кодом (Python + Cypher) и объяснением подхода, чтобы из вашего «лингвистического графа» (`knowledge_map_core` — JSON / Neo4j) извлекать **паттерны последовательностей действий** и оценивать, какие последовательности **успешно**/**неуспешно** приводят к конкретной цели.

Я даю два рабочих варианта:

- Вариант A — если вы храните граф в **Neo4j** (рекомендую при больших графах и сложных запросах).
- Вариант B — если у вас просто JSON-лексикон/граф и вы хотите всё делать в памяти с **NetworkX / чистым Python**.

В обоих вариантах результат — список паттернов (последовательностей действий) с метриками: support (частота), success_rate, confidence, lift/odds и дополнительные оценки.

---

### Идея и допущения

1. В графе есть узлы действий (label `Action`) и узлы целей (label `Goal`) либо какие-то маркеры достижения цели.
2. Для каждого наблюдаемого пути/экземпляра у вас есть метка результата: `success: True/False` (либо можно извлечь success по атрибутам конечного состояния).
3. Мы извлекаем все пути от действий к цели (или все пути между событиями), превращаем путь в последовательность action-id / action-type и агрегируем статистику по уникальным последовательностям и их подпоследовательностям (n-граммы).
4. Параметры: максимальная длина пути `L`, минимальная поддержка `min_support`.

### Вариант A — Neo4j + Python (neo4j-driver)

Пример использует официальный `neo4j`-driver. Идея: выбрать все релевантные пути (например `MATCH p=(a:Action)-[*1..L]->(g:Goal {id:$goal_id}) RETURN p`) и вернуть их в Python для подсчёта паттернов.

```python
# Требует: pip install neo4j pandas
from neo4j import GraphDatabase
from collections import Counter, defaultdict
import pandas as pd

URI = "bolt://localhost:7687"
AUTH = ("neo4j", "password")  # замените

driver = GraphDatabase.driver(URI, auth=AUTH)

def extract_paths_from_neo4j(goal_id, max_len=6, sample_limit=10000):
    """
    Возвращает список кортежей: (action_sequence, success_flag)
    action_sequence = [action_type_or_id, ...]
    success_flag = True/False (определяется по свойству конечного узла)
    """
    query = """
    MATCH p = (start)-[*1..$max_len]->(g:Goal {id:$goal_id})
    WHERE ALL(n IN nodes(p) WHERE (labels(n) = [] OR 'Action' IN labels(n) OR 'Goal' IN labels(n) OR 'State' IN labels(n))) 
    RETURN p LIMIT $limit
    """
    results = []
    with driver.session() as session:
        for record in session.run(query, max_len=max_len, goal_id=goal_id, limit=sample_limit):
            path = record["p"]
            nodes = path.nodes
            # извлекаем последовательность действий: любые ноды с меткой Action
            seq = []
            for n in nodes:
                labels = list(n.labels)
                if 'Action' in labels:
                    # сохраняем идентификатор/тип — настроить на ваш JSON/свойства
                    seq.append(n.get("action_type") or n.get("action_id") or n.id)
            # определяем success: если конечный узел (g) имеет success=true
            g = nodes[-1]
            success = bool(g.get("success", False))
            if seq:
                results.append((tuple(seq), success))
    return results

def aggregate_patterns(seq_success_pairs, max_pattern_len=4):
    """
    Извлекает все подпоследовательности (contiguous n-grams) до длины max_pattern_len
    Возвращает DataFrame с метриками для каждого паттерна.
    """
    counts = Counter()
    success_counts = Counter()
    total_sequences = 0
    for seq, success in seq_success_pairs:
        total_sequences += 1
        n = len(seq)
        for L in range(1, min(n, max_pattern_len)+1):
            for i in range(n - L + 1):
                p = tuple(seq[i:i+L])
                counts[p] += 1
                if success:
                    success_counts[p] += 1

    rows = []
    for p, cnt in counts.items():
        succ = success_counts.get(p, 0)
        rows.append({
            "pattern": p,
            "support": cnt,
            "success_count": succ,
            "success_rate": succ / cnt,
        })
    df = pd.DataFrame(rows)
    df = df.sort_values(by=["support","success_rate"], ascending=[False, False]).reset_index(drop=True)
    return df

# Пример использования
pairs = extract_paths_from_neo4j(goal_id="goal_42", max_len=8, sample_limit=20000)
df_patterns = aggregate_patterns(pairs, max_pattern_len=4)
print(df_patterns.head(30))
```

Пояснения:

- `extract_paths_from_neo4j` гибкий: подстройте `MATCH` под вашу схемy, добавьте WHERE по времени, пользователю и т.д.
- `aggregate_patterns` считает **континуальные подпоследовательности (n-граммы)**. Можно расширить до непоследовательных или частичных шаблонов (subgraph matching).

### Вариант B — JSON → NetworkX (в памяти)

Если у вас JSON-структура (ваш «лингвистический граф»), то сначала загружаем JSON и строим ориентированный граф. Примерный формат JSON предполагается такой (поправьте под себя):

```json
{
  "nodes":[{"id":"a1","type":"Action","action_type":"click"},{"id":"s1","type":"State"},...],
  "edges":[{"from":"a1","to":"s1","type":"causes"}, ...],
  "instances":[{"trace": ["a1","a2","a3","g1"], "success": true}, ...]  # если у вас есть журналные трассы
}
```

Код:

```python
# Требует: pip install networkx pandas
import json
import networkx as nx
from collections import Counter
import pandas as pd

def load_graph_from_json(path):
    with open(path, "r", encoding="utf-8") as f:
        data = json.load(f)
    G = nx.DiGraph()
    for n in data.get("nodes", []):
        G.add_node(n["id"], **n)
    for e in data.get("edges", []):
        G.add_edge(e["from"], e["to"], **e)
    return G, data.get("instances", None)

def extract_sequences_from_traces(instances, id_to_action_type=None):
    """
    Если у вас есть готовые трассы (instances), используйте их — быстрее и корректнее.
    instances: list of {"trace": [node_ids...], "success": bool}
    """
    pairs = []
    for inst in instances:
        seq = []
        for node_id in inst["trace"]:
            t = id_to_action_type.get(node_id) if id_to_action_type else None
            # если node_id - Action, добавляем
            # В простом случае: берем node_id как action идентификатор
            seq.append(node_id)
        pairs.append((tuple(seq), bool(inst.get("success", False))))
    return pairs

def extract_paths_from_graph(G, start_nodes, goal_nodes, max_len=6):
    # Находит простые пути из любой start->goal (релевантно если трассы отсутствуют)
    pairs = []
    for s in start_nodes:
        for g in goal_nodes:
            try:
                for path in nx.all_simple_paths(G, source=s, target=g, cutoff=max_len):
                    seq = [n for n in path if G.nodes[n].get("type") == "Action"]
                    # Если goal node имеет success атрибут:
                    success = bool(G.nodes[g].get("success", False))
                    if seq:
                        pairs.append((tuple(seq), success))
            except nx.NetworkXNoPath:
                continue
    return pairs

# Пример агрегации (можно переиспользовать aggregate_patterns выше)
def run_json_pipeline(json_path):
    G, instances = load_graph_from_json(json_path)
    # карта id->action_type (если нужно нормализовать)
    id_to_action_type = {n: G.nodes[n].get("action_type") for n in G.nodes if G.nodes[n].get("type")=="Action"}
    if instances:
        pairs = extract_sequences_from_traces(instances, id_to_action_type)
    else:
        start_nodes = [n for n,d in G.nodes(data=True) if d.get("type") == "Action" and d.get("is_entry")]
        goal_nodes = [n for n,d in G.nodes(data=True) if d.get("type") == "Goal"]
        pairs = extract_paths_from_graph(G, start_nodes, goal_nodes, max_len=6)
    df = aggregate_patterns(pairs, max_pattern_len=4)
    return df
```

### Метрики и ранжирование паттернов

Для каждого паттерна `P` полезно вычислить:

- `support = count(P)` — абсолютная частота.
- `success_rate = successes(P) / support`.
- `confidence(P -> success) = success_rate`.
- `lift = success_rate / global_success_rate` — насколько лучше чем среднее.
- `odds_ratio` — отношение шансов успеха/неуспеха.
- `avg_steps_to_goal` — среднее расстояние от начала паттерна до достижения цели (если доступны временные или позиционные данные).
- `time_cost` — средняя временная стоимость (если в данных есть duration).

Добавьте эти столбцы в DataFrame и сортируйте по приоритету (например: `support * lift`).

Пример расширения метрик:

```python
def compute_extra_metrics(df, total_successes, total_trials):
    global_success_rate = total_successes / total_trials
    df['lift'] = df['success_rate'] / global_success_rate
    df['support_ratio'] = df['support'] / total_trials
    # odds ratio
    df['odds'] = df['success_rate'] / (1 - df['success_rate'] + 1e-9)
    global_odds = global_success_rate / (1 - global_success_rate + 1e-9)
    df['odds_ratio'] = df['odds'] / global_odds
    return df
```

`total_successes` и `total_trials` берутся из ваших `seq_success_pairs`.

### Простая реализация поиска «критических шагов»

Иногда полезно не только считать паттерны, но и искать **влияние отдельного шага**:

- Уберите шаг `A` из последовательностей (симуляция контрфакта) и посчитайте, как изменится success_rate.
- Разность success_rate показывает «вклад/влияние» шага.

Пример:

```python
def evaluate_step_impact(pairs, step):
    # pairs: [(seq, success), ...]
    with_step = [s for s in pairs if step in s[0]]
    without_step = [s for s in pairs if step not in s[0]]
    def sr(lst):
        if not lst: return None
        return sum(1 for _,succ in lst if succ) / len(lst)
    return {
        "step": step,
        "count_with": len(with_step),
        "count_without": len(without_step),
        "sr_with": sr(with_step),
        "sr_without": sr(without_step),
        "delta": (sr(with_step) or 0) - (sr(without_step) or 0)
    }
```

## Запрос

Допустим я получил паттерны успеха и неуспеха, на размеченных данных. Как я могу применить их для генерации ещё не известных следующих действий, к цели до которой может вести только одна посредственная связь, полученная в результате обратного планирования, и это без нейросетей. Как пример, одна из идей что цепочки должны быть уникальными, по этому по разному соединяя элементы уже существующих цепочек в новую цепочку, можно сгенерировать что то новое и возможно оно может достигать какой то поставленной цели. Предложи сам и другие способы.


Алгоритм обратного планирования тоже нужно написать используя лингвистику, логику и можно даже нейросети.
Посредственная связь это значит что между высокоуровневыми действиями скорее всего есть ещё блоки которые описывают более низкоуровневые действия, но которых ещё нет в данных.

## Ответ

Отлично — у вас есть размеченные паттерны успеха/неуспеха. Ниже — набор практичных, исполнимых без нейросетей (и с вариантами, где нейросети можно подключить опционально) способов **генерировать новые последовательности действий**, когда между высокоуровневым действием и целью есть только «посредственная связь» (т.е. известно, что между ними должны быть низкоуровневые шаги, которых нет в данных). Для каждого способа — идея, алгоритм (псевдо/реальный Python), критерии оценки и советы по отбраковке/ранжированию. В конце — алгоритм обратного планирования, который сочетает лингвистику, логику и (опционально) нейросети.

### 1. Общая идея и входные данные

Предположим, у вас есть:

- `patterns` — таблица/словарь паттернов: каждая запись = `(pattern_tuple, support, success_rate, lift, ...)`.
- `mediator` — посредственная связь/высокоуровневое действие `M` (строка или узел), которое связывает предыдущее действие `A_high` с целью `G`, но не содержит детализации.
- (Опционально) лексические ресурсы: словарь `verb -> possible_subactions` (от VerbNet/FrameNet-подобного), или правило разложения.
- (Опционально) модель для семантической совместимости (можно и без неё).

Цель: сгенерировать новые candidate sequences `S = [.., a_i, ..., M_sub1, M_sub2, ..., goal]` которые не встречались в обучении, и оценить их вероятность успеха.

### 2. Метод 1 — Рекомбинация существующих паттернов (без нейросетей)

Идея: берём знакомые успешные цепочки и генерируем новые, склеивая их частями, при этом соблюдая порядок и «семантическую совместимость».

Алгоритм (описание):

1. Набор исходных паттернов `P_success` и `P_fail`.
2. Делим каждый паттерн на куски (contiguous n-grams) длиной 1..k.
3. Собираем кандидаты, комбинируя куски из разных паттернов, при этом требуем:

   * начало/конец совпадают с нужными высокоуровневыми шагами (начало = `A_high`, конец = `G` через `M`),
   * избегаем уже существующей точной цепочки (uniqueness),
   * применяем фильтр по «совместимости»: два соседних кусочка можно склеивать, если последний элемент первого и первый элемент второго встречались рядом в обучении хотя бы `min_adj_support` раз (или имеют совместимость по семантике).
4. Оцениваем каждый кандидат композитной скорой (см. секцию «Оценка кандидатов»).

Пример функции (Python):

```python
from collections import defaultdict
import itertools

def generate_by_recombination(patterns, start, mediator, goal, max_piece=3, min_adj_support=2, max_candidates=1000):
    """
    patterns: list of tuples (pattern_tuple, support, success_rate)
    start, mediator, goal: tokens
    """
    # build adjacency counts for compatibility test
    adj_counts = defaultdict(int)
    for pat, sup, sr in patterns:
        for i in range(len(pat)-1):
            adj_counts[(pat[i], pat[i+1])] += 1

    # create pieces (contiguous substrings) from successful patterns
    pieces = []
    for pat, sup, sr in patterns:
        if sr >= 0.5 and sup >= 2:  # only reasonably successful pieces
            n = len(pat)
            for L in range(1, min(max_piece, n)+1):
                for i in range(n - L + 1):
                    pieces.append(tuple(pat[i:i+L]))

    # deduplicate and sort by support heuristic (longer + more support first)
    pieces = list({p for p in pieces})
    # quick scoring: longer pieces preferred
    pieces.sort(key=lambda p: (-len(p), p))

    candidates = set()
    for a in pieces:
        if a[0] != start and a[-1] != mediator and a[0] != mediator:
            pass
    # naive beam: join 2-3 pieces ensuring adjacency compatibility
    for p1, p2 in itertools.permutations(pieces, 2):
        if len(candidates) >= max_candidates: break
        # ensure end->start adjacency exists or mediator insertion allowed
        if (p1[-1], p2[0]) in adj_counts and adj_counts[(p1[-1], p2[0])] >= min_adj_support:
            seq = p1 + p2
            # ensure it begins with start and ends with mediator/goal somewhere
            if seq[0] == start and (mediator in seq or seq[-1] == goal):
                candidates.add(seq)
    return list(candidates)
```

Советы:

- Сохраняйте уникальность (ровно не было в обучающем наборе).
- Ограничивайте длину и число кандидатов.

### 3. Метод 2 — Заполнение пропусков (gap-filling) через лингвистическую декомпозицию

Идея: медиатор `M` — высокоуровневый глагол/действие. Используем лингвистические ресурсы (фреймы, роль-предикатную информацию), чтобы предложить низкоуровневые подзадачи.

Шаги:

1. Возьмите `M` (например: "prepare_report"). Получите семантическую раму: аргументы, типичные поддействия (сбор данных, очистка, форматирование, проверка).
2. На основании существующих паттернов найдите фрагменты, которые реализуют эти подзадачи (по семантическому соответствию).
3. Генерируйте последовательность из таких фрагментов в логическом порядке (с учётом предикатов/предусловий).

Пример псевдо-функции (зависит от лексических словарей; без них — используйте эвристики по морфологии/словоформе):

```python
def expand_mediator_with_lexicon(mediator_token, lexicon, pattern_index):
    """
    lexicon: dict mediator -> list of candidate low-level action tokens or templates
    pattern_index: map action_token -> patterns containing it (for support)
    """
    candidates = lexicon.get(mediator_token, [])
    # rank candidates by how many successful patterns they appear in
    scored = []
    for cand_seq in candidates:  # cand_seq can be tuple of tokens
        support = sum(pattern_index.get(tok, 0) for tok in cand_seq)
        scored.append((cand_seq, support))
    scored.sort(key=lambda x: -x[1])
    return [s for s,_ in scored]
```

Где взять `lexicon`:

- вручную (экспертная база),
- автоматически: по частым зависимостям в корпусе (если перед словами часто стоят суб-действия),
- через VerbNet/FrameNet (они дают типичные семантические роли и сценарии).

### 4. Метод 3 — Constraint-based генерация + SAT/SMT

Идея: формализовать, какие предусловия нужны для `M_sub_i` и какие эффекты дают — и решать задачу составления цепочки как CSP: последовательность действий, которая приводит от имеющихся предпосылок к цели.

Подход:

- Для каждого низкоуровневого шага определите предусловия (pre) и эффекты (add/delete).
- Решите задачу планирования (как STRIPS) с *поиском в обратном направлении* (backward search): старт = goal, применяем операторы в обратном (ундо) направлении, пока не дойдём до доступных предпосылок.

Это классический символический планировщик — без нейросетей. Можно использовать готовые логические решатели или писать DFS/BFS.

Псевдокод обратного поиска:

```
def backward_search(goal_state, operators, initial_state, depth_limit):
    frontier = [goal_state]
    while frontier:
        state = frontier.pop()
        if state subset of initial_state: return plan
        for op in operators:
            if op.add intersects state:
                new_state = (state - op.add) union op.pre
                if depth < depth_limit:
                    push new_state with op appended to plan
    return None
```

### 5. Метод 4 — Абдуктивное/аналогическое обоснование

Идея: найти паттерн в обучении, который *частично* соответствует вашей высокоуровневой схеме, и «подставить» недостающие шаги, используя аналогию.

Алгоритм:

1. Найти топ-k паттернов, которые содержат `M` или похожий по лексическому/семантическому признаку.
2. Для кажого такого паттерна убрать `M` и посмотреть, какие низкоуровневые шаги на его месте стоят.
3. «Склеить» эти наборы шагов в новых кандидатах (в стиле кросс-валидации/канонической замены).

### 6. Метод 5 — Поиск с монте-карловским деревом (MCTS) без NN

Идея: используйте MCTS, где симуляции — случайная выборка расширений (gap-filling по лексикону / рекомбинация). Каждый узел хранит статистику успеха (оценку из обученных паттернов). Это даёт эффективный поиск в огромном дереве вариантов без нейросетей.

Ключевые элементы:

- `selection`: UCB1
- `expansion`: вставляем одну возможную детализированную развертку медиатора
- `simulation`: симулируем до достижения goal либо до глубины, используя вероятности успеха n-грамм
- `backprop`: обновляем оценки.

### 7. Оценка кандидатов (scoring)

Для каждого candidate sequence `S` давайте скор:

- `score = α * estimated_success_prob + β * novelty + γ * (support_penalty_by_length)`
  где:

  * `estimated_success_prob` — комбинированная оценка, полученная из success_rate паттернов/подпоследовательностей: можно аппроксимировать как произведение/усреднение success_rate входящих n-грамм, скор скорректированный на lift.
  * `novelty` — поощряет уникальные последовательности (например, Jaccard distance к ближайшей тренировочной последовательности).
  * `support_penalty_by_length` — штраф за излишнюю длину.
  * `α,β,γ` — гиперпараметры.

Пример функции оценки:

```python
def estimate_success_prob(candidate, pattern_stats, global_success_rate):
    # pattern_stats: dict pattern_tuple -> (support, success_rate)
    # break candidate into n-grams and combine
    probs = []
    n = len(candidate)
    for L in range(1, min(4,n)+1):
        for i in range(n-L+1):
            p = tuple(candidate[i:i+L])
            if p in pattern_stats:
                probs.append(pattern_stats[p][1])
    if not probs:
        return global_success_rate * 0.5  # very low prior
    # combine conservatively: weighted average biased to smaller n-grams
    return sum(probs)/len(probs)
```

### 8. Уникальность (uniqueness) — как требовать и поощрять

- Абсолютная уникальность: candidate != any_train_sequence.
- Степень уникальности: `novelty = 1 - max_jaccard(candidate, train_sequences)`.
- Можно требовать `novelty >= τ` или включать novelty в score.

### 9. Практический пайплайн (pseudo-end-to-end)

1. Получили `patterns` + `pattern_index` + `lexicon` (опционально).
2. Обратное планирование: от `goal` ищем высокоуровневые предшественники; нашли `M`.
3. Генерация кандидатов:

   * a) рекомбинация;
   * b) лингвистическая декомпозиция `M -> [m1,m2,..]`;
   * c) constraint-based STRIPS backward filling;
   * d) MCTS поиском, комбинируя (a,b,c).
4. Оценка кандидатов: `estimate_success_prob` + novelty + длина.
5. Отбор топ-N кандидатов, симуляции/тестирование (если есть среда) или экспертная валидация.

### 10. Алгоритм обратного планирования (конкретно с лингвистикой + логикой + опционально NN)

Описание шагов и псевдокод:

1. Start: `G` (goal state or goal token).
2. Find high-level parents `H = {h | exists pattern ending with h -> G }`.
3. For each `h`:

   * If direct path `h->G` is strong (high support, high success_rate) — done.
   * Else: mark `h` as mediator. Need to expand `h` into `{m1,..,mk}`.
4. Expand mediator `h`:

   * (Linguistic) Use lexicon/frames to propose candidate subactions.
   * (Pattern mining) Find n-grams that often occur *between* actions of this semantic class.
   * (Logic) Apply STRIPS-like backward chaining: what preconditions are required for G? Which operators produce those preconditions? Recurse.
   * (Optional NN) Use seq2seq or transformer to predict plausible low-level steps, then filter them by pattern statistics.
5. Combine expansions with upstream actions from training set using recombination rules.
6. Score and return plans.

Псевдокод (упрощённо):

```
def backward_plan(goal, patterns, lexicon, operators, initial_state):
    parents = find_parents_of_goal(patterns, goal)
    plans = []
    for h in parents:
        if strong_edge(h, goal): plans.append([h, goal]); continue
        expansions = expand_mediator(h, lexicon, patterns, operators)
        for exp in expansions:
            candidate = combine(upstream_patterns_for(h), exp, [goal])
            score = evaluate(candidate)
            plans.append((candidate, score))
    return sorted(plans, key=lambda x:-x[1])
```

## Запрос

Важно ли что бы действия были обязательно связаны с целями для которых они выполняются? Или достижимость цели может быть просто true/false, а действия могут быть без привязки к цели? Важно помнить что любое действие может быть целью и наоборот.

## Ответ

Короткий ответ — нет, действия **не обязательно** должны быть заранее «привязаны» к целям. Но выбор между явной привязкой и свободной моделью сильно влияет на всё: как вы храните данные, какие алгоритмы применяете (частотный майнинг, обратное планирование, causal inference), и как вы интерпретируете результаты. Ниже — практическое разбор и рекомендации, чтобы вы могли принять осознанное решение и настроить `knowledge_map_core` и алгоритмы под оба варианта (явная привязка ↔ действия как «цели» тоже).

### 1) Что значит «действие привязано к цели» vs «нет привязки»

- **Привязано**: в данных/графе у каждой операции есть явная метка/отношение `intended_for` / `subgoal_of` / `achieves` указывающее на цель(и). Это — supervision/label, которое говорит «это действие выполняется для этой цели».
- **Не привязано**: в логах есть просто последовательности действий и для каждой последовательности есть итог `success: True/False` по некоторой цели (или вообще бинарный результат). Действия сами по себе не несут метки «для какой цели выполнены».

Важно: в вашей предметной области одно и то же действие может выступать и как шаг, и как цель (например, «собрать отчёт» — действие в одной трассе, цель в другой). Архитектура должна это поддерживать.

### 2) Последствия выбора

Если действия **привязаны к целям** (явно):

- Плюсы:

  * Легче вычислять условные вероятности `P(success | sequence, goal)` и `P(success | action, goal)`.
  * Обратное планирование проще: можно прямо искать паттерны, специфичные для цели.
  * Меньше неоднозначности при оценке вкладов шагов.
- Минусы:

  * Требуется разметка/логика для указания целей при записи данных (доп. усилия).
  * Реалистичные логи часто не имеют таких меток — нужна постфактум-атрибуция.

Если действия **не привязаны**:

- Плюсы:

  * Нет всплывающей разметки — легче собирать данные.
  * Можно находить универсальные паттерны, переносимые между целями.
- Минусы:

  * Вы теряете специфичную для цели связь; алгоритмы должны выводить соответствие действий → цель как скрытую переменную (сложнее).
  * Возможность «ошибочной» генерации планов, которые хороши в среднем, но не для конкретной цели.

### 3) Рекомендации по представлению в `knowledge_map_core`

Лучше поддержать оба варианта: храните явные ссылки, но допускайте их отсутствие.

Пример расширенной записи узла/трассы (JSON-поле):

```
{
  "trace_id": "t123",
  "steps": [
    {"id":"a1","token":"open_file","timestamp":..., "meta":{"actor":"u1"}},
    {"id":"a2","token":"extract_table", ...}
  ],
  "goal": "prepare_report",     # optional — может быть null
  "success": true,
  "intent": ["prepare_report","summarize_data"],  # optional list of intents
  "annotations": [{"action_id":"a2", "intended_for":"prepare_report"}]  # optional per-action mapping
}
```

- `goal` и `intent` — явные метки цели (может быть несколько).
- `annotations` — локальные привязки конкретных действий к целям (если известны).
- Всегда сохраняйте `success` (True/False) и контекст (actor, time, env), потому что они нужны для отнесения действия к конкретной цели/условиям.

### 4) Как учесть, что «любое действие может быть целью и наоборот»

- Сделайте узлы в графе **универсальными**: узел имеет типы/tags: `Action`, `Goal`, `State`. Эти теги — просто метки; узел может иметь одновременно `Action` и `Goal`.
- Отношения: `:INTENDED_FOR`, `:ACHIEVES`, `:PART_OF`, `:SUBGOAL_OF`, `:FOLLOWS`, `:CAUSED_BY`. Наличие разных отношений разрешит гибкую семантику.
- При майнинге паттернов рассматривайте и направление отношения: иногда удобней анализировать пути `Action -> State -> Goal`, иногда — `Goal <- Action`.

### 5) Если у вас нет привязки: стратегии вывести соответствие действию ↔ цели

1. **Атрибуция по временной близости / трассам**
   Если у вас есть лог-трейсы с goal-level метками в конце (или мета `success` по цели), вы можете считать, что все действия в трассе «участвуют» в достижении этой цели. Тогда строите `P(success | action, goal)` по подсчёту:

   ```
   count(action in traces with goal & success) / count(action in traces with goal)
   ```

   — простое и часто эффективное приближение.

2. **Association mining (частотные правила)**
   Ищите частые правила вида `action => goal` или `subsequence => goal` (специфично для каждой цели) с support/confidence/lift. Это даёт вероятностную привязку.

3. **EM / Latent variable (когда цель полностью скрыта)**
   Модель: каждая траектория имеет скрытую целевую метку; действия генерируются условно на цели. Запустите EM: E-step — априорные распределения целей для каждой траектории; M-step — обновить `P(action | goal)` и `P(goal)`. Это полезно, если у вас множество целей и нет явной метки.

4. **Кластеризация траекторий**
   Кластеризуйте последовательности/фичи (tf-idf на токены, n-граммы, embedding) — кластеры часто соответствуют целям/задачам. Затем вручную или автоматически привяжите кластеры к целям.

5. **Казуальные методы / A/B / интервенции**
   Если возможно — экспериментируйте: выполните/отключите действие и смотрите влияние на достижение цели. Это gold standard для причинности.

### 6) Как менять алгоритмы генерации/оценки в зависимости от статуса привязки

- **Если есть привязка**: при генерации планов ориентируйтесь на `patterns_by_goal[goal]`. Оценивайте `P(success | candidate, goal)` прямо из статистики goal-специфичных паттернов.
- **Если нет привязки**: оценка должна учитывать два уровня:

  1. `P(success | candidate)` — глобальная успешность без знания цели.
  2. `P(goal | candidate)` — вероятность, какой цели служит candidate (получается через ассоц. правила / EM / кластеризацию).
     Финальный скор: `sum_goal P(goal | candidate) * P(success | candidate, goal)` (модель смешивания).

### 7) Обратное планирование с учётом отсутствия/наличия привязки

Подходы:

- **Если цель известна** — классический backward chaining / STRIPS + gap-filling (как я описывал ранее). Пользуйтесь goal-specific паттернами и лексиконом для декомпозиции.
- **Если цель неизвестна** — сначала детектируйте/предсказывайте цель(и) для данного контекста/начального шага (кластер/EM/правила), затем применяйте backward planning для наиболее вероятных целей (top-k).
- **Если действие может быть целью** — в backward search позволите применять операции, которые сами могут быть целями; то есть состояние цели моделируется как предикат, а действие может иметь эффект, который заменяет предикат. Это естественно в STRIPS-планере, где цель — набор предикатов.

### 8) Конкретные вычисления (формулы и короткий код)

Вычисление условной вероятности успеха для действия и цели из трасс:

```python
from collections import defaultdict

# traces: list of {"steps":[tokens...], "goal":goal_or_None, "success":bool}
def compute_P_action_goal(traces):
    counts = defaultdict(int)
    succ = defaultdict(int)
    for t in traces:
        g = t.get("goal")
        for a in t["steps"]:
            counts[(a,g)] += 1
            if t["success"]:
                succ[(a,g)] += 1
    probs = {}
    for k in counts:
        probs[k] = succ[k] / counts[k]
    return probs  # dict (action,goal) -> P(success | action, goal)
```

Если `goal` отсутствует (None), you can compute global `P(success | action)` similarly and also `P(goal | action)` via counts of goals observed in traces that include action.

### 9) Практические рекомендации — что я бы сделал на вашем месте

1. **Сохранять мета-данные целей, когда это возможно.** Даже «слабая» разметка (`goal` на трассе, список возможных intents) сильно повышает качество планирования.
2. **Поддерживать гибкую нотацию узлов** (action/goal flags) — чтобы одно и то же узло могло быть и целью.
3. **Если нет разметки — строить EM / кластеризацию** по трассам, чтобы выявить скрытые цели, и затем использовать goal-specific майнинг.
4. **Использовать смешанную стратегию при генерации**: комбинировать рекомбинацию, лингвистическое декомпозицию и constraint-based (STRIPS) заполнение. Но при отсутствии привязки обязательно учитывать `P(goal | candidate)`.
5. **Оценивать кандидаты по ожидаемой пригодности для цели**, а не только по глобальной успешности.

### 10) Итог (коротко)

- Действия **не обязаны** иметь явную привязку к целям — это рабочая модель. Но наличие привязки делает все downstream-задачи (оценка, генерация, планирование) проще и точнее.
- Сделайте структуру данных гибкой: храните `goal` и `per-action annotations` опционально, поддерживайте роли `Action/Goal`.
- При отсутствии привязки используйте статистические/латентные методы (association mining, EM, кластеризация) чтобы вывести соответствия.
- Всегда рассчитывайте и используйте условные вероятности `P(success|action, goal)` и `P(goal|action)` — они ключ к корректной генерации новых последовательностей.
