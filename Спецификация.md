# Спецификация Карты Знаний

Цель проекта Карты Знаний: ускорить науку, через структурирование знаний, для создания терапии старения и для продления жизни человеку.

- Микросервисная архитектура
- Есть возможность преобразовывать PDF в Markdown
- Текст Markdown должен преобразовываться в триплеты Языка Знаний
- В интерфейсе триплеты должны превращаться в обычный текст или карту знаний
- Сервер должен считать количество заходов на сайт и количество уникальных пользователей
- Веб-приложение должно быть защищено от злоумышленников

## Каноничные данные из которых должна состоять научная статья. Новый формат научных статей

- Эти данные должны быть предоставлены при создании новой статьи сразу в нужном для Карты Знаний формате.
- Должна быть возможность через классические или AI алгоритмы извлекать эти данные из cуществующих научных статей.
- Вне зависимости от способа это то что должно быть получено в итоге из статьи и должно проверяться валидатором при написании статьи.
- В интерфейсе Карты Знаний, должны быть показаны примеры каждого из пунктов при наведении на иконку вопроса.
- Это может помогать в планировании исследования.

Структурные строки:

  - Обозначение: `metadata`
  - Поля
    - DOI
    - Название статьи

    - Журнал

    - Выпуск
    - Страницы

    - Конфликт интересов (список)
    - Регистрация исследования
- Универсальное поле для прямого создания утверждения из триплета
  - Обозначение: `statement`
  - Поля
    1. Субъект
    2. Предикат
    3. Объект
- Цель исследования (Формулировка научной задачи, проверка эффекта воздействия А на B)
  - Обознвачение: `goal`
  - Поля
    1. Субъект
    2. Предикат
    3. Объект
- Поле со свободным форматом — сплошным текстом, для чего нет полей
  - Обознвачение: `text`
  - Поля
    - Текст
- Гипотеза
  - Обозначение: `hypothesis`
  - Поля

        3. Объект

        2. Предикат опровержения
        3. Объект опровержения
  - Комментарии
    - Что пытаемся опровергнуть?
    - Пояснение почему нужно именно опровержение — ❗
- Предпосылки — граф с онтологией, из которой исходит исследователь (Утверждения на которые он опирался. Контекст). На какие знания в виде утверждений опираемся? Знания-зависимаости.
  - Обозначение: `prerequisite`
  - Поля:
    - Список утверждений (список)
- Что ожидаем получить после исследования?
  - Обозначение: `expectations`
    - Поля:
      - Список утверждений (список)

- Дизайн исследования ❗
  - Обозначение: `research_design`
  - Поля
    - Тип исследования
      - Case Report (Отчет по одному случаю) — описание одного пациента
      - Case Series (Отчёт по нескольким случаям) — описание нескольких похожих случаев
      - Статья A реплицирует статью B — Репликация — независимое повторение (воспроизведение) существующего исследования
        - Противоречия или поддержание с существующими статьями
      - Original Research (Оригинальное исследование) — должны давать новые данные
      - Review (Обзор) — анализирует несколько существующих исследований в одной статье (хуже мета-анализа). Новых экспериментов нет
      - Systematic Review (Систематический обзор) — делается по протоколу, где будут искать статьи, какие статьи включат и какие исключат
      - Статья мета-анализ — проводит точный расчёт исследований по размеру эффекта среди огромного количества статей (считается самым сильным доказательством)
      - Clinical Trial (Клиническое исследование) — проводится на людях, имеет 4 фазы
        - Фаза I — безопасность, переносимость, дозировка; обычно небольшое число здоровых добровольцев.
        - Фаза II — эффективность и подбор дозы у пациентов.
        - Фаза III — подтверждение эффективности и безопасности на большой группе пациентов, сравнение со стандартом/плацебо.
        - Фаза IV — наблюдение после регистрации: долгосрочная эффективность и редкие побочные эффекты.
    - Рандомизация (рандомизированное контролируемое исследование, RCT) (чекбокс)
    - Ослепление (чекбокс)

    - Размер эффекта
    - Confidence Interval
    - Мощность исследования
    - Репликации
    - Тип исследования
    - Рандомизация
    - Ослепление
    - Контрольная группа
    - Риск систематической ошибки
    - Метаанализ
    - Биологический механизм
    - Количество независимых лабораторий

## Канонический реестр структурных типов

Каноническим источником идентификаторов структурных строк является `shared/knowledge/knowledge_contracts/block_types.py`. `api/src/schemas/block_types.py` является тонким реэкспортом этого реестра; клиентская копия типов не может быть самостоятельным источником истины. Пайплайн должен поддерживать весь реестр, но создавать строку только при наличии подтверждения в исходной статье или в её явных библиографических метаданных. Отсутствующий в статье тип не заполняется пустым значением и не создаётся искусственно.

Текущий реестр содержит следующие типы: `metadata`, `statement`, `goal`, `text`, `hypothesis`, `prerequisite`, `expectations`, `research_design`, `material`, `method`, `experiment`, `inclusion_exclusion_criteria`, `biological_mechanism`, `impact_goal`, `intervention`, `animal_model`, `animal_group`, `entity`, `definition`, `assumptions`, `sample_size`, `data_source`, `probability_value`, `variance`, `effect_size`, `statistical_power`, `confidence_interval`, `magnitude_value`, `formula`, `causal_graph`, `identifiability_criteria`, `result`, `statistical_processing`, `claim`, `limitations`, `side_findings`, `side_effects`, `post_claims`, `open_questions`, `novelty`, `versions`, `future_research_suggestions`, `reference`, `link_with_aging`, `image`, `code`, `funding`, `interest_conflict`, `scientific_knowledge_value`, `action`, `experiment_step`, `finding`, `relation`, `temporal_relation`.

При типизации подтверждённого фрагмента сначала выбирается наиболее конкретный структурный тип, чьи обязательные поля прямо подтверждены исходным unit. Универсальный `statement` (T4) используется последним, только когда более подходящего специализированного типа нет; наличие грамматического триплета само по себе не делает T4 приоритетным. Это правило не разрешает терять модальность, отрицание, величины или контекст при переходе к специализированному типу.

Каждая строка должна иметь `schemaVersion: 2`, уникальный `instanceId`, порядок `order`, объект `data` и `data.provenance`. В `provenance` сохраняются идентификатор исходной ревизии, идентификаторы предложений и точные диапазоны исходного текста. Промежуточные семантические идентификаторы в provenance не используются. Контейнерные типы могут ссылаться на другие структурные строки только UUID-ссылками; текст статьи не дублируется в ссылочном поле. `metadata` является единственным singleton-типом и создаётся не более одного раза на статью.


## Язык Знаний

Определение на языке спецификаций (БНФ Формы Бэкуса — Наура):
```bash
Statement ::= Identifier ":" Subject "→" Predicate "→" Object
Subject ::= Concept | Statement | Literal | ActionOnStatement
Object ::= Concept | Statement | Literal
ActionOnStatement ::= ActionOperator "(" StatementRef ")"
ActionOperator ::= "identify_subjects"
```

- Утверждение образует триплет с UUID идентификатором
- Язык Знаний является вычислимым
- Если объект или субъект триплета содержит идентификатор утверждения то должна быть функция раскрывающая все зависимые утверждения, то есть вместо идентификаторов подставляется триплет на который он указывает. Триплеты считаются раскрытыми если ни в одном не осталось идентификатора который может раскрыться
- Контекст — совокупность всех раскрытых триплетов текущего триплета
- Одно утверждение должно описывать ровно одно отношение между двумя объектами или объектом и одним значением. Subject и Object не должны содержать другого самостоятельного утверждения. Predicate должен выражать ровно одну семантическую связь.

- Subject и Object
  - один самостоятельный объект/понятие или одно literal-значение
  - выражается одной именной группой (noun phrase) либо литерал
  - не содержит отдельного/второго утверждения
  - не содержит и / или, относительного придаточного, причинного/условного предложения
- Исключение к поверхностной именной группе Subject — типизированное `ActionOnStatement`: действие над ровно одним явно представленным атомарным утверждением. Его аргумент хранится ссылкой, а не копией придаточного предложения. На первом этапе канонический оператор — только `identify_subjects`: идентифицировать сущности в позиции Subject целевого утверждения, удовлетворяющие его Predicate/Object с сохранением модальности. Это **не** означает «установить истинность утверждения». Неподдерживаемые операторы не подменяются свободным текстом.
- В DSL прямого `statement` это кодируется `sub=<краткая именная метка действия> | subop=identify_subjects | subref=B<n> | pred=<одна связь> | obj=<одно значение> | unit=S<n>`. `subop` и `subref` обязательны вместе; метка `sub` нужна для чтения, но семантика Subject определяется парой оператор/ссылка. `subref` указывает только на структурную строку прямого триплета, которая даёт ровно одно Assertion (`statement`, `goal`, `entity`, `claim`, `action`). При сохранении временный B-тег разрешается в UUID этой строки; адаптер Assertion разрешает его в единственный `assertionId`. Ссылка не создаёт dependency-ребро автоматически.
- Пример S7: `B T4 B1 | sub=modifiable factors | pred=may_predict | obj=long-term cognitive decline in the elderly with adequate daily functionality | unit=S7` и `B T4 B2 | sub=identifying modifiable factors | subop=identify_subjects | subref=B1 | pred=is | obj=critical | unit=S7`. Запрещено повторять `that may predict ...` внутри `sub=` второй строки: именно эту связь уже выражают B1 и `subref=B1`.
- При разбиении перечисления дополнения направление отношения неизменно: для `X may include A and B` нужны `X may_include A` и `X may_include B`, а не `A/B may_include X`; `may` относится к каждой строке. Из фразы `poor sleep quality and quantity` допустимы `poor sleep quality` и `poor sleep quantity`, но нельзя придумывать направление изменения или эффект. Для `This work reports the methodology and descriptive characteristics ...` самореференциальное описание статьи сохраняется как `text` (T3) с точным текстом, а явно названный долгосрочный мультидисциплинарный дизайн, тема и семилетнее наблюдение — как `research_design` (T11). Эта фраза сама по себе не описывает выполненную процедуру T21 и не требует T4-триплетов о статье.
- Predicate
  - одна семантическая связь;
  - в Knowledge Language хранится как один канонический предикат, например inhibits, causes, measured_in, located_in;
  - исходно в тексте он может состоять из нескольких слов, но после нормализации превращается в один идентификатор.

## DAG граф карты знаний

### Нормативная модель

В этом разделе термин «карта знаний» означает структуру данных, а «Карта Знаний» — проект. Карта знаний — ориентированный ациклический граф зависимостей (`KnowledgeMapDAG`), а не произвольный граф редактора, статьи или лингвистического разбора.

- Вершина DAG — только атомарное утверждение (`Assertion`): один `Subject → Predicate → Object`, одно семантическое отношение, с отрицанием, эпистемическим статусом, контекстом и provenance.
- `ArticleBlock` (структурная строка) — входной типизированный носитель факта, контекста или доказательства. Он не становится вершиной DAG автоматически.
- Концепт, литерал, действие, эксперимент, группа животных и цель являются значениями либо ролями утверждения, а не самостоятельными вершинами без утверждения. Цель — это атомарное утверждение с ролью `goal`.
- Ребро `A → B` означает: утверждение A необходимо для обоснования, выполнения, механистического объяснения или достижения утверждения B. Путь направлен от предпосылок и фактов к выводу или цели.
- Ссылки Subject/Object на другие утверждения нужны для раскрытия и семантического разрешения; они не создают ребро DAG автоматически.
- Семантические, причинные, временные и ссылочные отношения образуют отдельный граф ссылок. В нём допустимы циклы. В `KnowledgeMapDAG` входят только проверенные dependency-рёбра.
- Промежуточный семантический слой не используется: в production-пайплайне нет отдельного этапа, сущностей или provenance-идентификаторов такого слоя.

### Инварианты DAG

1. У каждого узла есть стабильный `assertionId`, атомарный триплет, роль, `sourceBlockIds`, `sourceSpans` и статус построения.
2. Нельзя создавать искусственный узел из пустой строки, метаданных, ссылки, UUID или технической сущности (`SourceRevision`, `ArticleBlock`).
3. Одна пара вершин может иметь несколько независимых семантических обоснований, но в DAG хранится одно дедуплицированное ребро на пару и класс зависимости; все источники сохраняются в provenance ребра.
4. Самопетли и циклы dependency-рёбер не исправляются разворотом или удалением «для укладки»: ребро отклоняется, а причина записывается в диагностике. Семантический цикл сохраняется вне DAG.
5. Визуализация получает только валидированный `KnowledgeMapDAG`; она не строит связи из всех UUID-полей и не меняет направление рёбер.

### Алгоритм преобразования структурных строк

Алгоритм применяется к каждой строке независимо, затем объединяет результаты по явным ссылкам и provenance. Внешние знания, неявные текстовые совпадения и fallback-поиск endpoint'ов запрещены.

1. Валидировать `blockType`, обязательные поля, `instanceId`, `data.provenance` и диапазон исходной ревизии.
2. Выбрать адаптер по `blockType` из таблицы ниже. Адаптер возвращает `0..N` атомарных утверждений, кандидаты семантических/зависимостных рёбер, контекст и диагностику.
3. Для строк с явными Subject/Predicate/Object нормализовать один триплет. Координация, несколько независимых предикатов или результатов разбиваются только по исходному предложению на несколько атомарных утверждений.
   `subop`/`subref` структурной строки разрешаются как `ActionOnStatement` только после построения атомарного Assertion целевой строки. Неразрешённая, самоссылочная либо указывающая на строку с `0..N` Assertion ссылка отклоняется с диагностикой; текстовым совпадением она не заменяется.
4. Для текстовых утверждений извлечь только явно выраженные в source span субъект, предикат и объект. Если субъект, объект либо связь не определяются однозначно, не создавать узел: сохранить строку как контекст и выдать диагностический код.
5. Разрешать конечные точки relation/temporal_relation только явными типизированными ссылками на конкретное утверждение. Если ссылка указывает на строку с несколькими утверждениями, нужен явный `assertionId`; без него ребро не строится.
6. Сначала сформировать семантический граф. В DAG переносить только явные dependency-предикаты (`depends_on`, `requires`, `prerequisite_for`, `decomposed_into`, `enables`) либо связи, прошедшие детерминированную/семантическую верификацию необходимости A для B.
7. Дедуплицировать ребро по `(sourceAssertionId, targetAssertionId, dependencyType)` с объединением provenance. Проверить ацикличность; циклический кандидат оставить в семантическом слое с диагностикой, но не включать в DAG.

| Класс адаптера | Типы структурных строк | Результат |
| --- | --- | --- |
| Контекст и доказательство | `metadata`, `text`, `versions`, `reference`, `image`, `code`, `funding`, `interest_conflict` | Не создают узел. Сохраняются как provenance, источник, цитата, медиа или метаданные утверждений. `image` обязателен для каждого source unit подписи рисунка/таблицы; факты из подписи дополнительно извлекаются самостоятельными типизированными строками. |
| Прямой триплет | `goal`, `statement`, `entity`, `claim`, `action` | Создают один атомарный узел из явных Subject/Predicate/Object. `goal` дополнительно получает роль цели. |
| Текстовое или типизированное утверждение | `hypothesis`, `prerequisite`, `expectations`, `research_design`, `material`, `method`, `experiment`, `inclusion_exclusion_criteria`, `biological_mechanism`, `impact_goal`, `intervention`, `animal_model`, `animal_group`, `definition`, `assumptions`, `sample_size`, `data_source`, `probability_value`, `variance`, `effect_size`, `statistical_power`, `confidence_interval`, `magnitude_value`, `formula`, `identifiability_criteria`, `result`, `statistical_processing`, `limitations`, `side_findings`, `side_effects`, `post_claims`, `open_questions`, `novelty`, `future_research_suggestions`, `link_with_aging`, `scientific_knowledge_value`, `experiment_step`, `finding` | Создают `0..N` утверждений только по явному смыслу полей и source span. Числа, интервалы, p-value и иные qualifiers принадлежат однозначно определённому утверждению; без такого владельца они остаются контекстом с диагностикой. |
| Вложенный граф | `causal_graph` | Не является `KnowledgeMapDAG`. Его явные вершины и рёбра могут быть разобраны теми же адаптерами как отдельные утверждения и semantic-кандидаты, иначе сохраняются как вложенный артефакт. |
| Явная связь | `relation`, `temporal_relation` | Не создают вершину сами по себе. Создают semantic-кандидат между явно указанными Assertion; в DAG попадают только после классификации как dependency и проверки цикла. |

### Подписи рисунков и таблиц

Подпись рисунка, таблицы, supplementary figure/table или extended data — знаниевый фрагмент исходной статьи, а не `non_assertional`-технический текст. Детектор распознаёт строку с меткой `Figure`/`Fig.`/`Table`/`Рисунок`/`Таблица` и включает все пересекающиеся с ней source units.

1. Для каждого такого source unit обязательна строка `image` (`T49`) с полем `caption` и точным provenance.
2. Каждое явно выраженное в подписи наблюдение, сравнение, число, метод, связь, ограничение или неопределённость преобразуется в отдельную строку подходящего типа и далее — в `0..N` Assertion по адаптеру. `image` не заменяет такое утверждение.
3. Если подпись только идентифицирует медиа-объект и не утверждает научный факт, создаётся только `image`; утверждение не выдумывается.
4. Преобразование считается неполным, если caption source unit не имеет `image`-строки. Полноту смыслового извлечения из подписи оценивают gold-метрики, а не лексическое совпадение.

### Метрики преобразования «Научная статья → структурные строки → карта знаний»

Контракт отчёта — `quality_metrics.version = 5`. Метрики относятся к прямому production-маршруту без промежуточного семантического слоя: `source revision → linguistic profile → DSL/ArticleBlock → semantic graph и KnowledgeMapDAG`. Число в отчёте — наблюдение, не доказательство научной истинности. `1.0` означает 100%; при нулевом знаменателе долевые метрики равны `1.0`, если отсутствие сущностей не является ошибкой.

**Gates.** Они не входят в усреднённый балл и блокируют принятие артефакта:

| Gate | Проверка |
| --- | --- |
| `linguistic_schema_valid`, `structural_schema_valid`, `knowledge_map_schema_valid` | Валидность соответствующих контрактов и ссылок. |
| `source_not_empty` | Ревизия источника содержит непустой текст. |
| `source_provenance_complete` | У каждой структурной строки есть хотя бы один корректный диапазон той же source revision. |
| `caption_conversion_complete` | Каждый распознанный caption source unit имеет `image` (`T49`) с тем же `unit`. |

**Наблюдаемые метрики текущего отчёта.** Это полный перечень полей, которые выдаёт реализация; они нужны для диагностики, не все являются целевыми KPI.

| Раздел и метрика | Определение и назначение |
| --- | --- |
| `linguistic.sentence_count`, `token_count`, `section_count`, `dependency_count`, `phrase_count` | Размер и полнота лингвистического слоя: число исходных предложений, токенов, Markdown-разделов, синтаксических зависимостей и фраз. Это контроль входа, не оценка смысла. |
| `linguistic.source_sentence_coverage` | Доля предложений, пересекаемых хотя бы одним provenance source span структурной строки. |
| `linguistic.semantic_token_fraction` | Доля токенов, пересекаемых provenance всех структурных строк. Она показывает покрытие исходника, но не семантическую полноту. |
| `structural_rows.row_count`, `block_types` | Общее число DSL/ArticleBlock и распределение по `blockType`; позволяют видеть чрезмерную компрессию или разрастание. |
| `structural_rows.statement_count` | Число текущих statement-like строк (`statement`, `claim`, `entity`, `action`); не равно числу Assertion будущего DAG. |
| `structural_rows.relation_row_count` | Число строк `relation` и `temporal_relation`, потенциальных семантических связей. |
| `structural_rows.provenance_completeness` | Доля строк с валидными source span. Значение ниже 1 нарушает gate. |
| `structural_rows.duplicate_fingerprint_candidates` | Число лишних точных совпадений `(blockType, data без tag/unit/source/provenance)`. Это кандидаты на проверку, а не автоматическое слияние: контекст и источники могут различаться. |
| `structural_rows.caption_row_count` | Число всех строк, provenance которых ссылается на распознанные caption units. |
| `structural_rows.caption_image_row_count` | Число `image`-строк для подписей; сравнивается с покрытием units, а не с числом файлов. |
| `structural_rows.caption_semantic_row_count` | Число не-`image` и не-`metadata` строк из подписей; индикатор, что содержательные подписи не были сведены к медиа-ярлыку. |
| `knowledge_map.node_count`, `semantic_edge_count` | Число вершин и разрешённых семантических рёбер в фактическом графовом артефакте. До миграции текущей реализации на Assertion-DAG это диагностические значения legacy Variant A, не соответствие нормативной модели выше. |
| `knowledge_map.link_resolvability` | Доля semantic edges, у которых обе конечные точки существуют среди node ids. |
| `knowledge_map.orphan_node_count`, `orphan_node_fraction` | Число и доля вершин без разрешённого инцидентного semantic edge. Одиночный факт допустим, поэтому это сигнал структуры, не gate. |
| `knowledge_map.weakly_connected_components` | Число слабосвязных компонент по разрешённым semantic edges; помогает увидеть фрагментацию карты. |
| `source_accounting.sentence_count`, `covered_sentence_count`, `uncovered_sentence_count` | Абсолютные значения для `source_sentence_coverage`; последнее должно быть нулём для полного извлечения. |
| `source_accounting.token_count`, `represented_token_count` | Абсолютные значения для `semantic_token_fraction`; нужны, чтобы доля была интерпретируема. |
| `source_accounting.caption_unit_count`, `caption_image_covered_unit_count`, `caption_image_coverage`, `uncovered_caption_unit_ids` | Число caption units, покрытых `image`, их доля и точный список пропусков. Непустой список нарушает `caption_conversion_complete`. |
| `evidence.blocks_total`, `blocks_supported`, `evidence_fraction`, `details` | Детерминированная лексическая эвристика: для строки сравниваются её текстовые термины с леммами provenance-предложения; `details` содержит результат по строке. Это лишь индикатор привязки к источнику: перефразировка и научная истинность ею не устанавливаются. |
| `quality.automated_components.structural_integrity`, `provenance`, `semantic_coverage`, `relation_resolution`, `graph_health` | Пять нормированных компонентов: валидность схем, полнота provenance, покрытие токенов, отношение разрешённых рёбер к relation rows и среднее разрешимости/неизолированности графа. |
| `quality.automated_score` | Временный диагностический балл `100 × Σ(component × 0.20)`. Он не является критерием научной корректности, не заменяет gates и должен быть пересмотрен после миграции на Assertion-DAG. |
| `quality.semantic_fidelity` | Текущее числовое значение `evidence_fraction`; не следует трактовать как entailment или factuality. |
| `manual_review.assertion_precision`, `assertion_recall`, `relation_f1`, `context_f1`, `modality_f1` | Пока имеют статус `requires_gold_standard`: сравнение с размеченным эталоном. |
| `manual_review.atomicity`, `scientific_faithfulness`, `absence_of_external_knowledge` | Пока имеют статус `requires_expert_review`: эксперт проверяет один факт на Assertion, верность статье и отсутствие привнесённых знаний. |

**Нормативные метрики следующей версии Assertion-DAG.** Они заменят либо уточнят временные прокси выше; baseline, пороги и доверительные интервалы задаются после размеченного корпуса и фиксируются с версиями модели, промпта, схемы и руководства разметки.

| `source_entailment_precision`, `external_knowledge_rate`, `scientific_faithfulness_rate` | Экспертная или NLI-проверка того, что утверждение следует из конкретного source span, не добавляет внешнее знание и не искажает статью. |
| `weighted_semantic_coverage`, `key_result_recall`, `limitations_recall`, `caption_semantic_recall` | Взвешенное по разделам Results/Discussion покрытие смысловых единиц, полнота ключевых результатов/ограничений и gold-recall явных фактов из подписей. |
| `duplicate_precision`, `duplicate_recall`, `duplicate_f1`, `uncertain_merge_rate` | Качество обнаружения эквивалентных Assertion. Кандидат создаётся exact/embedding-поиском, но `UNCERTAIN` никогда не сливается автоматически. |
| `entity_b_cubed_precision`, `entity_b_cubed_recall`, `entity_b_cubed_f1`, `concept_reuse_consistency` | Корректность нормализации и кластеризации сущностей, а также согласованность повторного использования концепта в одинаковом контексте. |
| `dag_acyclicity`, `dependency_provenance_completeness`, `goal_reachability`, `path_correctness` | Отсутствие циклов dependency-рёбер, provenance каждого ребра, достижимость цели от предпосылок и корректность путей по gold. |
| `competency_question_accuracy`, `regenerated_fact_fidelity`, `cross_stage_trace_completeness`, `error_cascade_rate` | Ответы карты на контрольные вопросы, верность восстановленных фактов, полная трасса assertion → row → source и доля ошибок, идущих из ранней стадии дальше. |
| `uncertainty_reduction_per_cost`, `downstream_task_utility` | Продуктовая метрика: снятая неопределённость на время/деньги/ресурсы и `(вероятность успеха × прирост информации × релевантность) / стоимость`. Не смешивается с качеством извлечения. |
| `run_stability`, `latency`, `cost`, `uncertainty_calibration` | Стабильность на повторных запусках, задержка, цена и соответствие заявленной уверенности фактической точности. |

Все P/R/F1 считаются на замороженном gold corpus, по статьям (не по отдельным строкам) с bootstrap доверительными интервалами. До появления gold запрещено выдавать прокси `semantic_token_fraction`, `evidence_fraction` или `automated_score` за precision, recall, factuality либо полноту смысла.

### Реестр промптов

Единственный нормативный формат ответа LLM для извлечения знаний — построчный DSL. JSON допустим только как транспортный протокол между сервисами и как формат хранения, но никогда не является форматом ответа модели или промежуточным языком извлечения. Промежуточный семантический слой и его сущности в промптах, схемах, provenance и артефактах запрещены.

| `prompt_id` | Версия | Статус | Назначение и контракт |
| --- | --- | --- | --- |
| `KM.ARTICLE_ROWS` | 95 | production | `source units → DSL ArticleBlock`. Выход — только DSL-строки `B T<code> B<tag> | ... | unit=S<n>`; заголовок состоит из трёх токенов, ключи берутся только из `DSL_FIELDS`, обязательные значения непустые, поля отделяются `|`, каждая строка заканчивается своим `unit=S<n>`. Каждое утверждение подтверждается и привязано к исходной единице. Разбор находит управляющий предикат до зависимых, сохраняет его отношение даже при неконечном/номинализованном аргументе и отдельно кодирует независимо выраженное вложенное утверждение. Поля T4 `sub/pred/obj` соответствуют исходным аргументным ролям: комплемент не переносится в субъект, copula остаётся в `pred`, complement — в `obj`, а `pred` не поглощает аргумент или второе утверждение. Каждый независимо адресуемый элемент списка, управляемого общим предикатом, имеет отдельную строку в исходном порядке; общие модификаторы сохраняются по грамматическому основанию. Документ, статья или авторы в роли субъекта сообщения о содержании задают метадискурс: полное signposting-предложение — T3 `content=`, не научное отношение; из комплемента извлекаются только явно выраженные утверждения. Вводные фразы без предикации не создают утверждение; анафора разрешается только при однозначном референте, соседние факты и единицы источника не переносятся. Тип выбирается по роли: T11 — дизайн/выборка и фазы, T25 — целочисленный размер выборки, T21 — метод/измерение, T36 — эмпирический результат; T4 — только при отсутствии подходящего специального типа. `n=` хранит лишь размер выборки; T21 — одна строка на цель измерения; полный T36 дополняется типизированными значениями T32/T28, когда требует схема. Независимый DSL-аудит проверяет полноту, точность, аргументные роли, привязку к источнику и ограничения схемы; коррекции следуют тем же правилам. Выход без JSON, прозы и Markdown. Пайплайн сохраняет прогресс батчей и возобновляется с последнего успешного батча. |
| `KM.GOAL_PLAN` | 2 | production | `цель → DSL structural rows` с ролью цели и явными dependency-кандидатами; не создаёт JSON-дерево и технические сущности Goal/Task/Step. |
| `KM.EVIDENCE_VIEW` | 2 | support | `канонические ArticleBlock/Assertion → DSL evidence view`. Не извлекает вторую независимую карту из статьи, не отбрасывает captions и не меняет provenance. |
| `KM.SENTENCE_ROWS` | 2 | support | `одно source unit → DSL rows` для локальной диагностики. Использует те же типы, modality, negation, provenance и запреты, что `KM.ARTICLE_ROWS`. |
| `KM.PDF_MARKDOWN` | 2 | support | `raw PDF + Docling → canonical Markdown`; сохраняет заголовки, таблицы, figure/figcaption и их точный порядок. Это не извлечение утверждений. |
| `KM.DATASET_ANNOTATION` | 2 | reference | Руководство ручной разметки gold: source spans, Assertion, context, relation и duplicate verdict `SAME/DIFFERENT/UNCERTAIN`; результат — DSL/gold, не GML/JSON-шаблон модели. |
| `KM.LEGACY_DOCUMENTATION` | 1 | reference | Исторические документы из `docs/`, `prompts/` и `personal_folder`. Они обязаны содержать явную ссылку на этот реестр и не могут задавать production-контракт. |

Для каждого production-вызова сохраняются `prompt_id`, `prompt_version`, версия схемы и версия руководства разметки. Промпт считается невалидным, если он требует JSON-ответ, промежуточный семантический слой, UUID как смысловую сущность, обязательное число строк/relations, relation из текстового совпадения или игнорирование подписи рисунка/таблицы.

Правила качества промпта:

1. Не оптимизировать число строк, покрытие токенов или число связей ценой ложных Assertion. Приоритет: schema/provenance gates, source entailment, assertion/relation/context/modality F1, caption semantic recall и duplicate F1.
2. `ArticleBlock` может содержать материал для нескольких Assertion; атомарность относится к каждому Assertion, а не к числу предикатов в structural row.
3. `relation` и `temporal_relation` допускаются только при явных typed `srcRef`/`tgtRef`; текст, UUID, ссылка и совпадение названия endpoint не разрешают.
4. Для duplicate-candidate embedding или exact match только предлагает кандидата; автоматическое слияние разрешено лишь при `SAME`, а `UNCERTAIN` сохраняется раздельно.
5. Caption source unit обязан получить `image`; фактическое содержание caption извлекается дополнительными типизированными строками.

### Политика циклов, слоёв и имён

- Биологическая обратная связь, корреляция и взаимная причинность не отменяются: они живут в семантическом графе и при необходимости разворачиваются во времени только как явно сформулированные разные утверждения.
- Алгоритм укладки не имеет права применять `convert_to_dag` к каноническим данным, так как разворот ребра меняет смысл утверждения.
- Имя `DEPENDS_ON` зарезервировано для зависимости утверждений в карте. Лингвистическая синтаксическая зависимость должна именоваться отдельно, например `SYNTACTIC_DEPENDS_ON`.

## Паттерны успешные и не успешные

- Успешным паттерном являются тот набор (граф) утверждений который приводит к положительному результату исследования или иначе, гипотеза подтвердилась (не опровергнута).
- Не успешным паттерном является тот набор (граф) утверждений который приводит к отрицательному (неправильному) результату исследования или иначе, гипотеза не подтвердилась или если исследование содержит ошибки в методах или дизайне исследования.
