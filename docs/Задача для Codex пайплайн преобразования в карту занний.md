# Архивная задача: преобразование полнотекстовой научной статьи в структурные строки и Карту Знаний

Ты работаешь над проектом **«Карта Знаний»**.

Твоя задача — реализовать и привести к единой архитектуре полный конвейер:

```text
Научная статья с полным текстом
    ↓
Лингвистический профиль
    ↓
Структурные строки (DSL)
    ↓
Карта Знаний
```

Актуальный прямой маршрут и требования определены в `Спецификация.md`; этот документ сохраняется только как исторический контекст.

Важно: сейчас нет доступа к инфраструктуре cloud.ru и нет гранта, так что используй временно локальную "Qwen3.8-4B-distill" вместо "DeepSeek V4 Flash" от cloud.ru, по адресу http://127.0.0.1:1234.

# 1. Язык

* Все промпты, предназначенные для LLM, должны быть написаны **на английском языке**.
* Все инструкции и системные сообщения внутри LLM-pipeline должны быть написаны **на английском языке**.
* Генерируемый LLM результат должен быть на **английском языке**.
* Исходная статья может быть на русском или другом языке.
* Исходный текст должен сохраняться без изменений.
* При переходе к нормализованному семантическому представлению используй канонический английский язык.
* Не допускается потеря научного смысла из-за перевода.

# 3. Главный принцип архитектуры

Разделяй три уровня.

```text
Текст
  ↓
Лингвистический профиль
  ↓
Структурные строки (DSL)
  ↓
Карта Знаний
```

Эти уровни выполняют разные задачи.

## Лингвистический профиль

Лингвистический профиль — это детерминированное описание исходного текста (предложения, токены, разделы и диапазоны), не самостоятельный семантический слой.

Основной принцип:

> При переходе от текста к лингвистическому профилю нельзя без необходимости терять информацию, которая может быть полезна для последующих этапов.

Лингвистический профиль должен сохранять достаточно информации для:

* восстановления смысла;
* анализа структуры выражения;
* поиска семантических паттернов;
* построения сложных концептов;
* привязки структурных строк к источнику;
* последующей проверки результата.

Лингвистический профиль должен быть **loss-minimizing representation**.

## Структурные строки

Структурные строки — это формальное представление знаний, полученное напрямую из source units с опорой на лингвистический профиль.

Они должны быть пригодны для:

* однозначного машинного разбора;
* создания концептов;
* создания атомарных утверждений;
* последующего построения Карты Знаний.

## Карта Знаний

Карта Знаний — ещё более высокий уровень абстракции.

Она предназначена для:

* визуализации;
* поиска графовых паттернов;
* логического вывода;
* силлогизмов;
* операций мышления;
* обнаружения новых связей;
* генерации новых знаний.

Не смешивай эти уровни.

---

# 4. Необходимо сохранить информацию между уровнями

Переход между уровнями должен выглядеть так:

```text
Source text
    ↓
Linguistic profile
    ↓
Structural DSL rows
    ↓
Knowledge Map
```

Каждый следующий уровень может быть более абстрактным, но должен иметь возможность ссылаться на предыдущий.

Нельзя допускать ситуацию:

```text
Source unit → Structural String
```

после которой невозможно определить, из какого фрагмента источника появилась структурная строка.

И аналогично:

```text
Knowledge Map assertion
    ↓
Structural String
    ↓
Source text
```

должен оставаться трассируемым.

---

# 5. Provenance обязателен

Каждый значимый элемент, извлечённый из статьи, должен сохранять provenance.

По возможности сохраняй:

* идентификатор статьи;
* раздел;
* предложение;
* исходный диапазон текста;
* положение в исходном документе;
* ссылку на соответствующую структурную строку;
* ссылку на соответствующее утверждение Карты Знаний.

Минимальная цепочка трассировки:

```text
Knowledge Map
    ↓
Structural String
    ↓
Source Span
    ↓
Article
```

Provenance должен быть отдельными метаданными, а не частью текста самого Subject/Predicate/Object.

---

# 6. Concept и Assertion — разные сущности

Обязательно различай:

## Concept

Концепт — самостоятельная семантическая единица.

Примеры:

```text
mouse
rodent
laboratory mouse
Acomys russatus
aging
clusterin
cellular senescence
```

Концепт не обязан иметь Predicate.

## Assertion

Утверждение выражает отношение:

```text
Subject → Predicate → Object
```

или для одноместного предиката:

```text
Subject → Predicate
```

Concept и Assertion нельзя считать одним и тем же типом сущности.

---

# 7. Концепт может существовать без предиката

Допускай узлы:

```text
C1: mouse
C2: rodent
C3: laboratory mouse
C4: Acomys russatus
C5: aging
```

Это не Assertions.

Это **Concept nodes**.

Их задача — представлять переиспользуемые единицы смысла.

---

# 8. Один Concept — один концепт

Не используй количество слов как критерий атомарности.

Например:

```text
laboratory mouse
```

может быть одним Concept.

```text
golden spiny mouse
```

может быть одним Concept.

```text
exceptional regenerative capacity
```

может быть одним Concept.

Но выражение:

```text
long-lived wild rodents closely related to laboratory mice
```

не должно автоматически рассматриваться как неделимый Concept, если внутри него есть самостоятельные концепты и отношения, которые могут быть полезны для поиска паттернов.

Его внутренняя семантическая структура должна быть представлена отдельными структурными строками только при явном подтверждении источником.

---

# 9. Сложные концепты

Сложный концепт может существовать как единый Concept на уровне структурной строки или Карты Знаний; его составные отношения фиксируются отдельными утверждениями при наличии явного источника.

Например:

```text
C1: aged golden spiny mouse
```

может иметь внутреннюю структуру:

```text
C1
├── is_a → mouse
├── is_a → spiny mouse
├── has_species → Acomys russatus
└── has_age_state → aged
```

Важно:

* внешний Concept может быть единым;
* внутренняя структура не должна теряться;
* один и тот же Concept должен переиспользоваться.

---

# 10. Assertion должен быть атомарным

Одно Assertion выражает **ровно одно семантическое отношение**.

Например:

```text
Rapamycin → inhibits → mTOR
```

и:

```text
Rapamycin → activates → autophagy
```

вместо:

```text
Rapamycin → inhibits mTOR and activates autophagy
```

---

# 11. Subject и Object должны ссылаться на единицы смысла

Subject/Object не должны быть произвольными строками из исходного текста.

Они должны ссылаться на:

* Concept;
* Assertion;
* допустимый Literal/Value.

Например:

```text
A1:
C1 → inhibits → C2
```

---

# 12. Рекурсивные ссылки

Assertion может использовать другое Assertion как Subject или Object.

Допустимы:

```text
Concept → Predicate → Concept
Concept → Predicate → Assertion
Assertion → Predicate → Concept
Assertion → Predicate → Assertion
```

Например:

```text
A1:
dormant signaling pathways → oppose → aging

A2:
long-lived wild rodents → can_reveal → A1
```

Ссылка на Assertion означает **всё Assertion целиком**.

---

# 13. Ссылки должны быть типизированы

Различай как минимум:

```text
ConceptReference
AssertionReference
Literal
```

Например:

```text
@C123
@A456
"4.5 years"
```

Не допускай неоднозначности, когда строка UUID сама по себе не позволяет определить, на какой тип объекта она ссылается.

---

# 14. Одноместные предикаты

Поддерживай одноместные предикаты:

```text
Subject → Predicate
```

Например:

```text
Acomys → is_resilient
```

Не создавай искусственный Object.

Но отсутствие Object само по себе не означает, что Predicate одноместный.

Арность должна быть:

* явно определена;
* либо однозначно выведена из семантики Predicate.

---

# 15. `is_a` / `subclass_of`

Отношение:

```text
is_a
subclass_of
```

используй для отношения подмножества/класса.

Например:

```text
spiny mouse → is_a → rodent
golden spiny mouse → is_a → spiny mouse
```

Это отношение должно быть пригодно для последующего логического наследования.

Не превращай `is_a` в простой текст.

---

# 16. Статус утверждений

Все новые Assertions по умолчанию имеют статус:

```text
hypothesized
```

Не превращай утверждение в `fact` только потому, что автор статьи формулирует его уверенно.

---

# 17. Модальность

Сохраняй:

* may;
* might;
* could;
* possible;
* likely;
* suggests;
* hypothesize;
* we posit;
* unknown;
* associated with;
* demonstrated;
* causes.

Не допускай автоматического усиления:

```text
may → does
associated_with → causes
hypothesis → fact
suggests → proves
```

---

# 18. Отрицание

Сохраняй отрицание.

Например:

```text
Acomys russatus → does_not_show → age-related increase
```

не должно превращаться в:

```text
Acomys russatus → shows → age-related increase
```

---

# 19. Сравнение

Сохраняй обе стороны и направление сравнения.

Например:

```text
A. russatus → has_lower_senescence_than → A. dimidiatus
```

не превращай в:

```text
A. russatus → has → lower senescence
```

если сравнение существенно.

---

# 20. Причинность

Не превращай:

* корреляцию;
* ассоциацию;
* совпадение;
* различие;
* temporal relation

в причинность.

Если источник прямо сообщает причинный эффект, причинность можно сохранить:

```text
clusterin administration → reduces → fibrosis
```

---

# 21. Контекст

Не теряй:

* species;
* age;
* sex;
* tissue;
* cell type;
* treatment;
* control;
* dose;
* time;
* environment;
* SPF/non-SPF;
* experimental condition.

Если удаление контекста изменяет смысл утверждения, контекст должен сохраниться.

---

# 22. Координации

Если один Predicate относится к нескольким объектам, разделяй отношения.

Например:

```text
aging → increases → Il1b
aging → increases → Ccr2
aging → increases → Cxcl1
```

А не создавай один Object:

```text
Il1b, Ccr2 and Cxcl1
```

если эти понятия должны быть независимо переиспользуемыми.

То же относится к нескольким Subject.

---

# 23. Не добавляй внешние знания

Преобразование статьи должно использовать только информацию источника.

Не добавляй:

* общеизвестные биологические знания;
* собственные интерпретации;
* сведения из других статей;
* логические выводы, если они не предусмотрены отдельным этапом вывода.

---

# 24. Extraction и inference должны быть разделены

Pipeline извлечения должен отвечать:

> Что содержится в статье?

А система reasoning должна отвечать:

> Что можно вывести из уже представленного знания?

Не смешивай эти задачи.

---

# 25. Лингвистический профиль сохраняет структуру исходного языка

Лингвистический профиль должен по возможности сохранять:

* токены;
* предложения;
* фразы;
* зависимости;
* модификаторы;
* отрицание;
* модальность;
* coreference;
* семантические роли;
* source spans;
* связи между частями фразы.

Не уничтожай детали лингвистического профиля ради упрощения дальнейшего этапа.

---

# 26. Каждый значимый токен должен быть представлен

Каждое слово исходного текста, имеющее значение для семантической структуры, должно иметь соответствующий узел или быть частью структурного узла, позволяющего однозначно восстановить его положение.

Необходимо сохранять связь между токеном и его исходной позицией.

Не обязательно превращать каждую пунктуацию в отдельный семантический узел, если текущая архитектура этого не требует, но нельзя терять информацию, необходимую для восстановления структуры.

---

# 27. Лингвистический профиль не является DAG

Лингвистический профиль может содержать сложные лингвистические структуры, coreference и другие связи.

Не вводи ограничение DAG на лингвистический профиль только потому, что Knowledge Map должна быть DAG.

Ограничения на ацикличность должны определяться отдельно для каждого слоя.

---

# 28. Knowledge Map — не копия лингвистического профиля

Knowledge Map должна быть компактнее лингвистического профиля.

Не переноси в Knowledge Map:

* все токены;
* все синтаксические связи;
* каждую служебную зависимость.

В Knowledge Map должны попадать только значимые концепты, утверждения и связи, необходимые для карты знаний.

---

# 29. Visual dependency ≠ semantic reference

То, что Assertion A ссылается на Assertion B, **не означает автоматически**, что между ними должна появиться визуальная dependency-edge на Knowledge Map.

Визуальное ребро должно означать именно смысловую зависимость, необходимую для прохождения по карте.

---

# 30. Knowledge Map должна быть пригодна для pattern matching

Представление должно поддерживать поиск структурных паттернов.

Например:

```text
A → inhibits → B
B → increases → C
```

или:

```text
A → is_a → B
B → causes → C
```

Алгоритм поиска должен работать по структуре графа, а не только по строковому или embedding-сходству.

---

# 31. Knowledge Map должна быть пригодна для reasoning

Проект должен иметь возможность в будущем выполнять:

* subclass inheritance;
* транзитивные выводы там, где они допустимы;
* силлогизмы;
* композицию отношений;
* обнаружение противоречий;
* поиск эквивалентных структур;
* поиск аналогичных механизмов;
* генерацию гипотез.

Структура данных должна этому не препятствовать.

---

# 32. Отображение Knowledge Map

Каждый визуальный блок карты должен разрешаться обратно в понятный человеку английский текст.

Пользователь не должен видеть внутренние UUID вместо смысла.

Например:

```text
internal:
@C123 → @P17 → @C456
```

должно отображаться как:

```text
Clusterin inhibits complement activation
```

---

# 33. Provenance не должен отображаться как часть знания

Источник, статья, страница, предложение и другие метаданные должны храниться отдельно.

Не нужно делать:

```text
Kim et al. 2026 → reports → clusterin inhibits ...
```

частью самого биологического Assertion, если это только provenance.

---

# 34. Структурные строки должны быть машинно-парсируемыми

LLM не должна выдавать свободный текст там, где нужен структурный результат.

Используй строгий формат, совместимый с существующей системой структурных строк.

Если формат уже определён проектом:

* не создавай второй формат;
* не дублируй существующую модель;
* расширяй существующую реализацию при необходимости.

---

# 35. LLM не должна напрямую управлять БД

LLM должна выдавать структурированный результат.

Проверка, нормализация, создание ID, запись в БД и установление связей должны выполняться кодом.

Не доверяй LLM:

* произвольные UUID;
* произвольные SQL/Cypher-запросы;
* изменение схемы БД;
* запись неподтверждённых данных.

---

# 36. Validation после каждого этапа

Нужны отдельные валидаторы:

```text
Structural String Validator
Knowledge Map Validator
```

Каждый этап должен проверяться до передачи результата дальше.

---


# 38. Structural String Validator

Проверяй:

* синтаксис;
* корректность Concept;
* корректность Assertion;
* корректность Predicate;
* арность Predicate;
* разрешение ссылок;
* отсутствие недопустимых типов ссылок;
* наличие provenance;
* сохранение отрицания;
* сохранение модальности.

---

# 39. Knowledge Map Validator

Проверяй:

* разрешение всех ссылок;
* отсутствие битых узлов;
* соответствие ожидаемой структуре;
* возможность восстановить display text;
* наличие provenance;
* корректность визуальных зависимостей;
* отсутствие циклов, если для данного графа они запрещены.

---

# 40. Ambiguity

Если модель не уверена:

* не выдумывай структуру;
* не добавляй внешний смысл;
* сохраняй исходную информацию в лингвистическом профиле и provenance;
* помечай результат как ambiguous/uncertain согласно существующей схеме;
* оставляй возможность последующей ручной проверки.

Цель — не 100% формализация любой ценой, а корректная формализация.

---

# 41. Уровни абстракции

Соблюдай:

```text
Linguistic profile
↓
детерминированная структура исходного текста

Structural Strings
↓
формализованные Concepts + Assertions

Knowledge Map
↓
компактный граф знаний и зависимостей
```

Нельзя использовать Knowledge Map как замену лингвистического профиля.

---

# 42. Повторное использование Concept

Один и тот же концепт должен по возможности иметь одну сущность.

Например:

```text
C1 = Acomys russatus
```

должен повторно использоваться в разных Assertions, а не создаваться заново для каждого предложения.

---

# 43. Контекст может создавать разные Concepts

Не объединяй автоматически одинаковые строки.

Например:

```text
clusterin gene
clusterin protein
clusterin expression
recombinant clusterin
```

могут быть разными Concepts.

Определяй их идентичность по смыслу и контексту.

---

# 44. Методы и эксперименты

Methods можно представлять в структуре знаний, если они важны для воспроизводимости и понимания результата.

Например:

```text
4-mm ear punch assay → used_to_measure → regeneration capacity
Western blot → measures → protein expression
RNA-seq → analyzes → transcriptome
```

Но техническая инструкция не должна автоматически превращаться в биологическое знание.

---

# 45. Числа и единицы

Сохраняй значимые:

* возраст;
* дозы;
* время;
* размеры;
* sample size;
* P-values;
* концентрации;
* температуры;
* другие измерения.

Единицы измерения обязательны.

---

# 46. Ограничения и неизвестность

Включай информацию о:

* неизвестных механизмах;
* недостатке данных;
* ограниченной выборке;
* невозможности выполнить анализ;
* различиях экспериментальных условий;
* необходимости будущих исследований.

Это часть научного знания, а не шум.

---

# 47. Discussion

Не превращай Discussion автоматически в Results.

Формулировки:

```text
one possible hypothesis
may
might
could
we posit
future studies
```

должны сохранять статус гипотезы/предложения.

---

# 48. Принцип минимального усиления

При любом преобразовании предпочитай:

```text
less information
```

ложной информации.

Не усиливай утверждение.

Не меняй:

```text
association → causation
possibility → fact
hypothesis → fact
prediction → observation
interpretation → result
```

---

# 49. Стабильные идентификаторы

Не используй display text как identity.

ID должен быть отделён от текста.

ID должен использоваться для связи между:

```text
Linguistic profile
Structural Strings
Concepts
Assertions
Knowledge Map
```

---

# 50. База данных

Сохраняй в БД:

1. исходный текст;
2. лингвистический профиль;
3. структурные строки;
4. Concepts;
5. Assertions;
6. Knowledge Map;
7. provenance;
8. связи между уровнями.

Не сохраняй только конечную Карту Знаний.

---

# 51. End-to-end traceability

Для любого блока Knowledge Map должно быть возможно получить:

```text
Knowledge Map block
    ↓
Knowledge Map entity
    ↓
Assertion / Concept
    ↓
Structural String
    ↓
Source span
    ↓
Original article
```

Это обязательное свойство архитектуры.

---

# 52. Работа с предоставленным примером

Используй:

`Immunometabolic resistors of aging in long-lived golden spiny mice`

как end-to-end тест.

Сначала обработай:

```text
.ru.md
```

затем:

```text
Linguistic profile
```

затем:

```text
Structural Strings
```

затем:

```text
Knowledge Map
```

Сравни результат с:

`knowledge_map_assertions_acomys.md`

Но не копируй результат вручную.

Используй его только как пример ожидаемой семантики и структуры.

---

# 53. Работа с существующим кодом

Перед изменением:

* найди текущую реализацию;
* пойми её зависимости;
* проверь существующие интерфейсы;
* проверь совместимость с БД;
* сохрани обратную совместимость, где это разумно.

Не создавай параллельную архитектуру без необходимости.

---

# 54. Конфликты в документации

Если документация, код или примеры противоречат друг другу:

1. зафиксируй конфликт;
2. определи, какая версия является текущей;
3. не скрывай конфликт;
4. приведи код и документацию к одному каноническому поведению.

Не делай молчаливую замену одной модели другой.

---

# 55. Изменение спецификации

Если для реализации необходимо изменить:

* схему;
* формат структурных строк;
* модель лингвистического профиля;
* модель БД;
* правила идентификаторов;
* API,

сначала проверь, можно ли решить задачу без изменения существующей спецификации.

Если изменение необходимо, внеси его последовательно во все зависимые компоненты и документацию.

---

# 56. Тестирование

Создай или обнови тесты для:

* лингвистический профиль;
* Structural Strings;
* Concepts;
* Assertions;
* Provenance;
* Validation;
* Knowledge Map;
* end-to-end pipeline.

Тесты должны проверять не только отсутствие исключений, но и семантическую структуру результата.

---

# 57. End-to-end test

Обязательно иметь тест:

```text
article
 → linguistic profile
 → Structural Strings
 → Knowledge Map
 → save to DB
 → load from DB
 → resolve display text
```

После загрузки из БД структура должна оставаться эквивалентной исходной.

---

# 58. Что делать сначала

Работай в следующем порядке:

1. Прочитать всю документацию.
2. Изучить существующий код.
3. Составить текущую модель данных.
4. Найти противоречия.
5. Определить каноническую модель.
6. Реализовать прямое преобразование source units в DSL структурных строк.
7. Реализовать Structural Strings → Knowledge Map.
8. Реализовать сохранение канонических артефактов в БД.
9. Реализовать provenance.
10. Реализовать validators.
11. Реализовать тесты.
12. Прогнать пример статьи.
13. Исправить обнаруженные проблемы.
14. Обновить документацию.

# 59. Финальное архитектурное требование

Итоговая система должна обеспечивать:

```text
                     ┌────────────────────┐
                     │   Original Article │
                     └──────────┬─────────┘
                                ↓
                     ┌────────────────────┐
                     │ Linguistic profile │
                     │ source-preserving  │
                     └──────────┬─────────┘
                                ↓
                     ┌────────────────────┐
                     │ Structural Strings │
                     │ Concepts/Assertions│
                     └──────────┬─────────┘
                                ↓
                     ┌────────────────────┐
                     │  Knowledge Map     │
                     │ reusable knowledge │
                     └──────────┬─────────┘
                                ↓
              ┌─────────────────┼──────────────────┐
              ↓                 ↓                  ↓
        Pattern Search       Reasoning       New Knowledge
```

На каждом этапе должна сохраняться трассируемость назад к исходному тексту.

---

# 60. Главный принцип

**Нижний уровень сохраняет информацию. Верхний уровень её структурирует и абстрагирует.**

Не уничтожай информацию лингвистического профиля только потому, что она не нужна текущему этапу.

Не подменяй:

* текст лингвистическим профилем;
* лингвистический профиль структурными строками;
* структурные строки Картой Знаний;
* извлечение логическим выводом.

Каждый уровень должен иметь собственное назначение.
