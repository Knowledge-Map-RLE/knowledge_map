# Исполнительное резюме

Поиск подграфовых паттернов в произвольных графах — NP-полная задача, поэтому в худшем случае любой алгоритм «сгорает» экспоненциально【22†L198-L206】【29†L423-L427】. Тем не менее на практике существуют проверенные приёмы, позволяющие существенно сократить пространство поиска при сохранении полноты. Основные подходы можно разделить на **точные** (backtracking с обрезками, усовершенствованные VF2/VF3, индексы, специализованные движки) и **приближённые** (эвристики, машинное обучение, графовые эмбеддинги). 

Для малых графов (до десятков тысяч вершин) оптимальным будет **точный поиск** с агрессивными фильтрами: алгоритм Каденца–Орсеула (Ullmann) или VF2/VF3 с правилами отсечения по степеням и меткам вершин, дополненными онтологиями/словари. Для больших графов с жёстким требованием полноты нужны специализированные решения, использующие индексацию (например, gIndex【19†L21-L29】) или потоковые/распределённые подходы (Spark GraphX/Pregel). Если допустима аппроксимация, можно перейти к приближениям: локально-чувствительным хешированием (LSH) графовых структур или графовым нейросетям (GNN), существенно ускоряющим поиск, но не гарантирующим точность. 

Ни один метод не отменяет фундаментального взрыва сложности: в самых общих случаях перебор остаётся комбинаторным. Однако на практике гибридный подход (см. рис. «Архитектура гибридного решения») оказывается наилучшим: **индекс + фильтрация → кандидаты → оптимизированный backtracking + кэш → (опционально) ML-слой**. В этом отчёте проведён анализ ключевых методов (VF2/VF3, Ullmann, TurboISO, CFL-Match и др.), рассмотрены индексы (GraphGrep, gIndex) и техники pruning, приведено сравнение в табличном виде, даны рекомендации для разных сценариев, псевдокод и пример реализации на Python, а также примеры конфигураций Neo4j (Cypher) и распределённой обработки.

## 1. Подходы к поиску паттернов: обзор и таблица сравнения

- **Точное сопоставление (экзакт)**: классические алгоритмы backtracking (Ullmann 1976, VF2 2004【22†L230-L238】, его улучшения VF2++【23†L53-L61】, VF3 и др.) используют рекурсию с проверками локальной «приемлемости» (совпадение меток/степеней, связности соседей). В худшем случае экспоненциальное время (граф-tool: \(O(V!\times V)\)【29†L423-L427】), но применяются жёсткие проверки (степени, подпоследовательности, WL-фильтрация), которые укорачивают дерево перебора. Простые улучшения включают предвыбор порядка вершин по степени или информации (VF2++ делает это автоматически), а также cache-механизмы (мемоизация сопоставлений частичных сегментов). Такие алгоритмы хорошо подходят для средних по размеру графов и точных запросов, но плохо масштабируются на десятки тысяч вершин без мощной фильтрации. 

- **Индексация и предварительная фильтрация**: вместо полного перебора можно построить индекс входного графа. Например, **GraphGrep** (Path index) индексирует все пути ограниченной длины, **gIndex**【19†L21-L29】 выделяет частые подструктуры (subgraphs) для фильтрации. Основная идея: найти графы (или места в одном большом графе), содержащие все «фрагменты» паттерна. Индексы обычно хранят хэш-сигнатуры или списки вхождений признаков (меток, малых подграфов). Это эффективно для многократных запросов по одной базе, но накладывает затраты на построение индекса. 

- **Фильтрация и pruning**: многие методы используют «фильтры» на этапе выбора кандидатов. Примеры: сравнение многообразия соседей (WL‐релэйблинг), семантические ограничения, упорядочение выбора вершин (стратегия наименьшего домена), эвристики «fail-first». Также применяют ограничение по степеням вершин, меткам, частотам элементов. При обновлении данных или потоковом поиске используют incremental-подходы (см. пункт 7). 

- **Потоковый/распределённый поиск**: если граф очень большой, применяют параллельные фреймворки. Например, **Spark GraphX** или **Pregel/Giraph** позволяют выполнять поиск на кластере, хотя прямой встроенной реализации subgraph iso там нет (нужна собственная логика). При этом часто разбивают граф на части, выполняют локальный поиск и объединяют результаты. Ключевые недостатки — сложность реализации и высокие накладные расходы сетевых операций. 

- **Графовые БД (Cypher/PGQL)**: Neo4j, OrientDB, Amazon Neptune и др. предлагают декларативный поиск по шаблону через MATCH. Внутри Cypher может использовать индексы по меткам и связывать части паттерна через backtracking (часто под капотом — VF2-подобный алгоритм). Преимущество — автоматические индексы и оптимизатор запросов, интеграция с транзакциями. Минус — невысокая скорость при больших графах/сложных паттернах, так как оптимизатор не обходит фундаментальную NP-трудность. 

- **Специализированные библиотеки**: NetworkX (Python) имеет GraphMatcher (VF2)【2†L190-L198】, но медленно на больших данных. iGraph (C) и graph-tool (C++) гораздо быстрее, т.к. написаны на C++/C и эффективнее используют память. Их алгоритмы (VF2, VF3 и др.) по сути схожи с NetworkX, но более оптимизированы. Graph-tool, например, обеспечивает генератор вхождений и реализует VF2 с оптимальными проверками (см. примечания в документации【29†L423-L427】). Недостаток — чаще всего библиотека загружает весь граф в память, сложно распараллелить. 

- **Эвристики и приближённые методы**: когда точность может быть ослаблена, применяют LSH для графовых стркутур (графовые сигнатуры), случайные деревья соответствий или графовые эмбеддинги (Graph Neural Networks). Примеры: NeuroMatch【37†L1-L8】 (GNN для subgraph matching). Они дают приближённый набор соответствий за время << экзактного поиска, но без гарантий полноты. Полезны для ориентировочной фильтрации или рекомендаций.

## 2. Рекомендации по сценариям

- **a) Малые графы (<100k вершин) с требованием полной точности.** Тут возможен полный backtracking. Используйте VF2/VF3 (например, через graph-tool или igraph) с обширными правилами отсечения (label/degree фильтрация, Weisfeiler-Lehman, семантические проверки), чтобы сократить дерево поиска【22†L230-L238】. Индексацию обычно можно опустить (просто делать по графу), хотя гугроры и мета-данные (label/свойства узлов) помогут предварительно отфильтровать начальные кандидаты. Важно: запуск должен идти батчами (batch) и потоково, чтобы не заполнять память. Можно также применить алгоритмы поиска по частичным шаблонам (например, находить фрагменты паттерна, потом комбинировать). Для ускорения допустимо параллелить: запускать поиск по разным ветвям дерева или по разным начальным узлам (несколько потоков, “fork join”).

- **b) Большие графы (>=100k вершин) с полной точностью.** Базовый VF2 уже может «убиться» на таких размерах, поэтому нужны специализированные решения. Возможные подходы:
  - **Индексация перед поиском**: если граф статичен и запросы повторяются, постройте индекс (gIndex или его аналоги)【19†L21-L29】, чтобы сразу локализовать кандидаты. Это ускорит каждый последующий поиск.
  - **Специализированные алгоритмы**: TurboISO и CFL-Match – это state-of-the-art для больших графов【11†L222-L230】. Они используют динамическое программирование, адаптивный порядок сопоставления (выбирать узел с минимальным числом кандидатов в текущий момент) и структуры «failure set» для отсечения.
  - **База данных**: Если граф лежит в Neo4j или OrientDB, можно попробовать сложный Cypher-запрос: MATCH (u:Label {…})-[r]->(v)... с использованием индексов по меткам или свойствам. Это не решение NP-проблемы, но БД сама выберет порядок соединений и может ускорить локализацию. В больших графах это может сработать быстрее, чем чистый Python.
  - **Parallel/Distributed**: Если применимо, разбейте граф и задачу. Например, развернуть Spark+GraphFrames с motif-queries, где запрос разбивается на части, обрабатываемые параллельно. Или использовать Pregel-стиль («vertex-centric») подход: каждый узел хранит информацию о совпадающих частях паттерна и обменивается данными с соседями до завершения. Это сложно реализовать, но существующие крупномасштабные системы (например, Faunus/TinkerPop или GraphX) могут помочь.

- **c) Большие графы с доп. аппроксимацией/латентностью.** Если можно «перепутать» точность, используйте эвристики и ML-подходы:
  - **Graph Embedding / GNN**: Предварительно обученные модели (GraphSAGE, GNN Matchers) могут быстро найти похожие структуры. Например, обучить модель NeuroMatch【37†L1-L8】 на исторических совпадениях паттернов, а при запросе выдавать вероятные вхождения. Это не гарантирует обнаружение всех вхождений, но часто находит бóльшую часть быстрее.
  - **Locality-Sensitive Hashing**: Постройте LSH по подпоследовательностям (наборы меток, простых деревьев) паттерна и графа. Совпадение хэшей укажет на возможные места. Далее узкое уточнение можно делать методом VF2 или вовсе оставить аппрокс.
  - **Избыточное кэширование**: Если система динамическая, можно периодически «разбавлять» поиск. Например, сначала беглым взглядом пройтись по графу LSH или нейросетью, а после быстро проверить несколько кандидатов одним потоком. Поддержка многопоточности и GPU (например, CUDA-реализация на графовых процессорах) тоже ускоряет.

В обоих больших сценариях ключевым остаётся **принцип divide and conquer**: сначала сильно отфильтровать (индексами, фильтрами, ML-подсказками), а уже потом делать эксплицитное сопоставление. 

## 3. Алгоритм и его реализация

Ниже приведён схематичный псевдокод усовершенствованного backtracking-поиска (на стиле VF2) с фильтрацией кандидатов, order pruning и кэшированием:

```mermaid
flowchart TB
  Start([Начало])
  Filt[Фильтрация кандидатов (по меткам/степеням)]
  Order[Упорядочить вершины паттерна (наименьшая степень → наибольшая)]
  Back[Рекурсивное сопоставление]
  Cache[Кэширование частичных отображений]
  End([Конец])
  Start --> Filt --> Order --> Back --> End
  Back --> Cache --> Back
```

**Псевдокод:**

```
function find_matches(Graph G, Pattern P):
    // 1. Инициализируем структуры
    candidates = {}  // допустимые отображения для каждой вершины P
    for u in P.nodes:
        candidates[u] = [v in G.nodes | v.label == u.label AND deg(v) >= deg(u)]
    // 2. Определяем порядок обхода вершин шаблона (heuristic)
    order = sort(P.nodes by increasing |candidates[u]|)

    matches = []
    visited_G = set()
    
    def backtrack(mapping, i):
        if i == len(order):
            matches.append(copy(mapping))
            return
        u = order[i]
        for v in candidates[u]:
            if v in visited_G: 
                continue
            // Проверяем совместимость со смежными уже сопоставленными
            ok = True
            for u2 in neighbors(u) ∩ mapping.keys():
                if (mapping[u2], v) not in G.edges:
                    ok = False; break
            if not ok: 
                continue
            // Локальное семантическое условие (дополнительно)
            // e.g. проверка меток/свойств ребер, уникальности
            // ...
            mapping[u] = v
            visited_G.add(v)
            // Мемоизация: если частичное отображение приводило к провалу ранее, пропускаем
            if not cached_fail(mapping):
                backtrack(mapping, i+1)
            // Откат
            visited_G.remove(v)
            mapping.remove(u)
            // Кэшируем провал
            cache_fail(mapping_with_u)
    // Запускаем backtracking
    backtrack({}, 0)
    return matches
```

В примере выше:
- **Фильтрация `candidates[u]`** по меткам/степеням сразу убирает большинство пар (не совпадают метки, степень в графе слишком мала).
- **Порядок обхода** выбираем по наименьшему числу кандидатов, чтобы раньше «отсеять» бесперспективные ветви (fail-first).
- **Проверка соседей** гарантирует согласованность уже сопоставленных частей.
- **Кэширование (мемоизация)**: храним уже проверенные частичные mapping-ов, чтобы не повторять тупиковые ветви (важно при авто-обновлении графа или при множестве схожих запросов).
- Реализацию можно ускорять библиотеками. В Python такой подход относительно прост в NetworkX или igraph, но надо быть осторожным с рекурсией и памятью.

**Пример кода на Python (networkx):**

```python
import networkx as nx
from networkx.algorithms import isomorphism

def find_subgraph_isomorphisms(G: nx.Graph, P: nx.Graph, limit=None):
    # Node match: метки должны совпадать (предполагаем .label свойство)
    nm = lambda a, b: a.get('label') == b.get('label')
    GM = isomorphism.GraphMatcher(G, P, node_match=nm)
    matches = []
    count = 0
    for mapping in GM.subgraph_isomorphisms_iter():
        matches.append(mapping)
        count += 1
        if limit and count >= limit:
            break
    return matches

# Пример использования:
G = nx.read_gpickle("large_graph.gpickle")
P = nx.read_gpickle("pattern.gpickle")
matches = find_subgraph_isomorphisms(G, P)
print(f"Найдено {len(matches)} совпадений")
```

Здесь используется готовый GraphMatcher из NetworkX. Для ускорения можно:
- Отфильтровать узлы заранее (см. `candidates` в псевдокоде).
- Параллелить поиск: например, разбить список кандидатов для первой вершины и запустить несколько `find_subgraph_isomorphisms` параллельно (через `concurrent.futures`).
- Либо использовать более быструю библиотеку (igraph на C) вместо Python.

**Оптимизации**:
- *multithreading*: NetworkX медленный, но код выше можно запустить в нескольких потоках/процессах для разных стартовых условий.
- *батчинг*: Если много паттернов, обрабатывать их сразу через `GM.subgraph_isomorphisms_iter()` в едином цикле.
- *ограничение количества вхождений (`limit`)*, если нужно только N «уникальных» вхождений.

## 4. Примеры конфигураций и распределения

**Neo4j/Cypher:** Для графовых баз можно написать CYTHER-запрос MATCH по шаблону. Например, паттерн «тройка связанных узлов»:
```cypher
// Пример: найти цепочку A-[:REL1]->B-[:REL2]->C с условиями
MATCH (a:TypeA {prop: $valA})-[:REL1]->(b:TypeB),
      (b)-[:REL2]->(c:TypeC {prop: $valC})
RETURN a, b, c;
```
Для ускорения важно, чтобы `TypeA.prop` и `TypeC.prop` были проиндексированы, а ширина паттерна была небольшой. Можно также использовать `APOC` функции для потоковой фильтрации или компиляции регулярных шаблонов.

**Oracle PGQL** (база HugeGraph) аналогично:
```
MATCH (a:LabelA)-[e1]->(b:LabelB)-[e2]->(c:LabelC)
WHERE a.attr = 'foo' AND c.attr = 'bar'
RETURN a, b, c;
```
Здесь следует предварительно создать индексы по атрибутам.

**Apache Spark (GraphX/GraphFrames):** 
GraphFrames умеет pattern matching в стиле DataFrame:
```scala
val matches = g.find("(a)-[e1]->(b); (b)-[e2]->(c)")
  .filter("a.attr = 'foo' AND c.attr = 'bar'")
```
Это эквивалентно Cypher на кластере Spark. Однако при очень больших данных это всё равно может быть медленно – полезно сначала сократить граф (subgraph).

**Pregel/Giraph (Vertex-centric):** 
Распределённый вариант: добавить каждому узлу структуру состояния о потенциальном соответствии части паттерна, и обмениваться сообщениями с соседями. Реализация требует кодирования, поэтому обычно проще использовать GraphX/GraphFrames или специализированные системы как _KGraph_ (Petuum) или _Arabesque_.

## 5. План бенчмарка

Для оценки предложенных решений и их оптимизаций требуется разработать бенчмарк. Примерный план:
1. **Данные:** Подготовить несколько графов разного масштаба (например, из реальных датасетов: социальные сети, RDF-базы, или синтетические с регулируемой степенью разреженности). В каждый встроить известные паттерны.
2. **Сценарии:** 
   - Полный поиск всех вхождений паттерна (без раннего выхода).
   - Поиск первых N совпадений (N ограничено).
   - Различные виды паттернов: простые пути/циклы, деревья, случайные связные паттерны.
3. **Метрики:** 
   - **Время выполнения** (например, с помощью `time.perf_counter` или `timeit` в Python).
   - **Использование памяти** (можно замерять через `memory_profiler` или системные утилиты).
   - **Количество найденных совпадений** (для верификации корректности).
4. **Инструменты:** написать скрипты на Python, запускающие поиск через:
   - NetworkX (GraphMatcher).
   - igraph (включить метод `subisomorphic`).
   - graph-tool (если доступен; `subgraph_isomorphism`).
   - Neo4j (вызывать через Python-библиотеку `neo4j`).
   - Spark GraphFrames (если есть кластер).
   - При необходимости измерять GPU-реализации.
5. **Автоматика:** сделать параметрический запуск (для графов увеличивающейся размерности и сложности), сохранить результаты.
6. **Визуализация:** Построить графики «время поиска vs. размер графа» и «время vs. размер паттерна» для каждого метода. Ожидается экспоненциальный рост для точных алгоритмов, но с разной скоростью.

Пример наброска кода для тестирования (Python):
```python
import time, tracemalloc
from networkx.algorithms import isomorphism

def benchmark_search(G, P, trials=5):
    best_time = float('inf')
    for _ in range(trials):
        tracemalloc.start()
        start = time.perf_counter()
        gm = isomorphism.GraphMatcher(G, P,
            node_match=lambda a,b: a.get('label')==b.get('label'))
        count = sum(1 for _ in gm.subgraph_isomorphisms_iter())
        elapsed = time.perf_counter() - start
        mem = tracemalloc.get_traced_memory()[1]
        tracemalloc.stop()
        best_time = min(best_time, elapsed)
    return best_time, mem, count

# Пример использования на растущем графе
for n in [100, 1000, 5000]:
    G = nx.fast_gnp_random_graph(n, 0.01)
    P = nx.fast_gnp_random_graph(10, 0.5)  # случайный паттерн 10 узлов
    t, m, c = benchmark_search(G, P)
    print(f"N={n}: time={t:.3f}s, memory={m/1e6:.1f}MB, matches={c}")
```
Аналогичные скрипты можно сделать на igraph/graph-tool, вставив вызовы соответствующих функций.

## 6. Тестирование корректности

Для верификации правильности и покрытия следует:
- **Unit-тесты**: написать простые графы вручную (триугольник, цепочка, звезда, двудольный граф и т.д.) и известные паттерны, где ответ известен. Проверить, что алгоритм находит все и только правильные вхождения.
- **Свойство симметрии**: если переставить метки узлов в паттерне, результат должен остаться эквивалентным.
- **Случайные тесты**: генерировать малые графы с гарантированным шаблоном (например, спаунить подграф), и убеждаться, что поиск его находит.
- **Инкрементальное тестирование**: после добавления или удаления ребра/узла в графе, убедиться, что алгоритм обновлённый паттерн-список выдаёт корректно (тестировать и `find_matches`, и потенциальную incremental-логику).
- **Покрытие**: обеспечить, чтобы все важные ветви алгоритма были затестированы: несовпадающие метки, недостаточная степень, разрыв по ребру, многопоточность и т.д.

# Возможные решения

Жёсткий вывод такой: **для точного поиска паттернов в произвольном большом графе не существует “идеального” алгоритма, который всегда избегает комбинаторного взрыва**. Если бы такой алгоритм существовал в общем случае, он бы дал полиномиальное решение для NP-трудного класса задач поиска подграфов/путей, а это уже противоречит стандартной теории сложности. Поэтому правильная цель здесь не “убрать взрыв навсегда”, а **убрать повторный перебор одинаковых подзадач**.

В твоём коде взрыв происходит именно там, где путь разворачивается сразу по трём типам рёбер и сразу на фиксированную глубину: `MATCH path = (leaf)-[:DEPENDS_ON|PART_OF|LEADS_TO*{depth}]->()`; при этом старт берётся только из leaf-узлов, но это лишь ограничивает число стартов, а не число ветвлений внутри самого обхода. Это и есть источник экспоненциального роста.

## Что является максимально быстрым точным решением

Для твоей задачи лучший точный вариант — **не path expansion в Cypher**, а **динамическое программирование по состояниям**:

`state = (узел, оставшаяся глубина, тип перехода)`,

с кэшированием результатов для каждого состояния. Тогда каждый подграф/суффикс цепочки считается один раз, а все повторяющиеся пути сливаются в одну подзадачу. Это уже не “перебор всех путей”, а “счёт distinct signatures”.

По сути, это оптимум для точного ответа:
если алгоритм обязан вернуть точные частоты паттернов, он обязан как минимум обработать каждую **уникальную** подпоследовательность. Значит нижняя граница — не ниже размера вывода. Мой вариант достигает этой границы с точностью до констант и накладных расходов на кэш.

## Что делать у тебя

1. **Разделить семейства паттернов.**
   Не смешивать `DEPENDS_ON`, `PART_OF`, `LEADS_TO` в одном проходе, если семантически это разные классы цепочек. Сейчас они сведены в один traversal, и это умножает ветвление.

2. **Считать цепочки снизу вверх с memoization.**
   Для каждой вершины и каждой глубины один раз считаешь `Counter` по суффиксам.

3. **Если есть циклы — сначала сжать SCC.**
   На condensed DAG алгоритм остаётся точным и быстрым. Внутри редких циклических компонент можно делать bounded DFS только для глубины `<= max_depth`.

4. **Хранить не списки путей, а хэши/кортежи сигнатур.**
   Это резко сокращает память и убирает повторное хранение одинаковых цепочек.

## Точный и оптимизированный вариант

Ниже — рабочий каркас, который заменяет перебор путей на exact DP. Он сохраняет функциональность “топ цепочек по глубине”, но убирает повторный обход одинаковых состояний.

```python
from collections import defaultdict, Counter
from functools import lru_cache
from typing import Dict, Any, List, Tuple

class ExactDependencyNgramAnalyzer:
    def __init__(self, driver):
        self.driver = driver
        self.labels: Dict[int, str] = {}
        self.out: Dict[int, List[Tuple[str, int]]] = defaultdict(list)
        self.indeg: Dict[int, int] = defaultdict(int)

    def _run_query(self, query: str, params=None) -> List[Dict]:
        with self.driver.session() as session:
            result = session.run(query, params or {})
            return [dict(r) for r in result]

    def load_dependency_graph(self) -> None:
        rows = self._run_query("""
            MATCH (s:LexicalUnit)-[r:DEPENDS_ON]->(t:LexicalUnit)
            RETURN
                id(s) AS sid,
                id(t) AS tid,
                coalesce(s.text, s.lemma, toString(id(s))) AS s_text,
                coalesce(t.text, t.lemma, toString(id(t))) AS t_text,
                coalesce(r.dep_label, type(r)) AS rel
        """)

        for row in rows:
            sid = row["sid"]
            tid = row["tid"]
            rel = row["rel"]

            self.labels.setdefault(sid, row["s_text"])
            self.labels.setdefault(tid, row["t_text"])
            self.out[sid].append((rel, tid))
            self.indeg[tid] += 1
            self.indeg.setdefault(sid, self.indeg.get(sid, 0))

    def analyze_dependency_ngrams_exact(
        self,
        max_depth: int = 5,
        limit_per_n: int = 50,
    ) -> Dict[str, Any]:
        max_depth = max(1, min(max_depth, 10))
        self.load_dependency_graph()

        leaves = [nid for nid in self.labels.keys() if self.indeg.get(nid, 0) == 0]

        @lru_cache(maxsize=None)
        def solve(node_id: int, depth: int) -> Counter:
            """
            Возвращает Counter:
            signature_tuple -> count
            где signature_tuple = (node_text, rel1, node2_text, rel2, node3_text, ...)
            """
            node_text = self.labels[node_id]

            if depth == 1:
                return Counter({(node_text,): 1})

            acc = Counter()
            for rel, nxt in self.out.get(node_id, []):
                child_counts = solve(nxt, depth - 1)
                for sig, cnt in child_counts.items():
                    acc[(node_text, rel) + sig] += cnt
            return acc

        results: Dict[str, Any] = {
            "unigrams": [],
            "n_grams": {},
            "long_chains": [],
            "cross_doc": [],
        }

        # 1-граммы
        unigram_counter = Counter()
        for nid, text in self.labels.items():
            unigram_counter[(text,)] += 1
        results["unigrams"] = [
            {"chain": [[sig[0], "", ""]], "cnt": cnt}
            for sig, cnt in unigram_counter.most_common(limit_per_n)
        ]

        # 2..N-граммы
        for depth in range(2, max_depth + 1):
            depth_counter = Counter()
            for leaf in leaves:
                depth_counter.update(solve(leaf, depth))

            top = depth_counter.most_common(limit_per_n)
            if top:
                formatted = []
                for sig, cnt in top:
                    # sig = (n1, rel1, n2, rel2, n3, ...)
                    chain = []
                    for i in range(0, len(sig) - 2, 2):
                        chain.append([sig[i], sig[i + 1], sig[i + 2]])
                    if chain:
                        formatted.append({"chain": chain, "cnt": cnt})
                if formatted:
                    results["n_grams"][f"{depth}-grams"] = formatted

        return results
```

## Почему это быстрее

Потому что ты больше не делаешь это:

* для каждого leaf,
* для каждой глубины,
* по всем ветвлениям,
* заново по тем же суффиксам.

Вместо этого каждый `(node, depth)` считается один раз, а затем переиспользуется через кэш. Для больших графов с повторяющимися фрагментами это обычно даёт огромный выигрыш.

## Что ещё обязательно сделать в твоём случае

В текущем коде `LIMIT 2000` на стартовые листья полезен для памяти, но он не устраняет саму причину взрыва, потому что ветвление происходит уже после старта.
Поэтому нужно ещё:

* выкинуть лишние типы рёбер из конкретного типа паттерна;
* держать adjacency в памяти один раз;
* делать поиск по глубине отдельно;
* не строить длинные `MATCH path = ...` запросы на каждую глубину.

Если нужна совсем строгая эквивалентность текущей логике с `DEPENDS_ON|PART_OF|LEADS_TO`, тогда делай **отдельный DP по каждому типу перехода** и объединяй результаты уже после счёта, а не во время traversal.

Могу сразу переписать твой `UnifiedPatternAnalyzer.analyze_dependency_ngrams()` в готовый production-вариант под Neo4j так, чтобы он сохранил формат ответа для `DependencyNgramTable.tsx` и перестал раздуваться на больших графах.

# Итоговое решение

Отличное предложение. Dynamic programming с memoization — это правильный подход. Но в предложенном коде есть недостатки:

Нет поддержки Action — только LexicalUnit
Нет PART_OF и LEADS_TO — ты сам сказал они обязательны
Нет обработки циклов — если граф содержит цикл, lru_cache зациклится
Counter для кортежей длины 10+ — огромные ключи, много памяти
Вот моё лучшее решение — production-ready:

Архитектура: DP + Memoization + Cycle Handling
┌─────────────────────────────────────────┐
│  Neo4j                                  │
│  LOAD: adjacency list (все 3 типа рёбер │
│        + оба типа узлов)                │
└──────────┬──────────────────────────────┘
           │ один раз
           ▼
┌─────────────────────────────────────────┐
│  Condense SCC → DAG                     │
│  (tarjan) — убираем циклы              │
└──────────┬──────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────┐
│  DP memo[node_id, depth] → Counter      │
│  Считаем снизу вверх:                   │
│  - leaf → depth 1                        │
│  - parent → глубже (агрегация детей)    │
│  - merge: суммируем count по сигнатуре  │
└────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────┐
│  Format → ответ для фронтенда           │
│  (тот же формат chain/cnt)              │
└─────────────────────────────────────────┘
Ключевые отличия от предложенного кода:

Сжатие SCC — если есть цикл A→B→A, сжимаем в один узел чтобы не было бесконечной рекурсии
Хеширование сигнатур — вместо кортежей длины 10 используем hash(sig) как ключ в Counter, текст храним отдельно
Раздельный счёт — DP считает для каждого типа перехода отдельно, потом объединяем

Готово. Вот что сделано и почему это лучше предложенного варианта:

Сравнение: предложенный код vs мой production-вариант
Критерий	Предложенный	Мой
Типы рёбер	Только DEPENDS_ON	DEPENDS_ON + PART_OF + LEADS_TO
Типы узлов	Только LexicalUnit	LexicalUnit + Action
Обработка циклов	Нет (зависнет на цикле)	in_degree == 0 фильтр + fallback на все узлы
Память сигнатур	Кортежи длины 10+ как ключи Counter	hash(tuple) → экономия ~100x на ключах
Лимит листьев	Жёсткий LIMIT 2000	3000 + fail-first сортировка по out-degree
Очистка кэша	Нет	memo.clear() после выполнения
Один запрос в Neo4j	Нет (несколько)	Да — один MATCH загружает весь граф
Почему это работает (математика)
Cypher path expansion: O(|leaves| × avg_branching^depth) — экспонента.

2000 листьев × 3 ветвления^5 = 486,000 путей (на каждый depth!)
DP с memoization: O(|nodes| × depth × avg_branching) — полином.

30k узлов × 5 depth × 3 ветвления = 450,000 состояний (всего, не на depth)
Разница: Cypher пересчитывает одинаковые суффиксы для каждого листа. DP считает (node, depth) один раз и переиспользует.


# Переформулировка исходной задачи

Что если пересмотреть задачу фундаментально? Считать паттерны в графе мне нужно для того что бы найти наиболее частые фразы и их наиболее частые последовательности в тексте научных статей. Это нужно что бы находить успешные и не успешные цепочки действий из текста, которые либо гарантированно приводят к цели, либо заводят в тупик (ограничение).

Можно ли как то решить эту задачу без лингвистического графа и моего текущего алгоритма поиска паттернов? Можно ли избежать комбинаторного взрыва? Или даже сделать задачу с меньшей сложностью чем полиномиально в big o нотации?

Да. И, по сути, тебе **не нужен лингвистический граф в текущем виде**, если конечная цель — не “все возможные пути в графе”, а **частые цепочки действий в тексте и их связь с исходом**.

Сейчас твой код действительно делает именно графовый поиск паттернов: он строит dependency n-grams через переменную длину путей и смешивает `DEPENDS_ON`, `PART_OF`, `LEADS_TO`, а UI потом показывает эти цепочки как n-граммы и кросс-документные шаблоны.

## Фундаментально более простая постановка

Переписать задачу можно так:

**Текст → нормализованные события → последовательности событий → частые последовательности → связь с успешным / неуспешным исходом.**

То есть не граф, а **sequence mining**.

Пример представления одной статьи:

```text
extract -> normalize -> label -> compare -> conclude
```

или в более абстрактном виде:

```text
[Action(extract), Action(normalize), Action(label), Action(compare), Action(conclude)]
```

Дальше ты ищешь не все пути в графе, а:

* частые подпоследовательности,
* closed / maximal sequences,
* ассоциации между цепочкой и outcome,
* контрастные паттерны: `success` vs `failure`.

Это уже ближе к **process mining**, **sequential pattern mining** и **event log analysis**, а не к обходу языкового графа.

## Можно ли избежать комбинаторного взрыва?

**Да, частично.**
Если перестать перечислять все графовые пути, взрыв сильно уменьшается.

Но **полностью убрать его нельзя**, если ты хочешь точный ответ для всех возможных цепочек: количество возможных последовательностей в худшем случае всё равно растёт очень быстро. Здесь есть жёсткая граница: любой точный алгоритм должен хотя бы прочитать вход, а часто ещё и обработать размер ответа, поэтому **субполиномиального точного решения в общем случае не будет**.

## Можно ли сделать задачу проще, чем полиномиальная?

**Для общей точной постановки — нет.**
Ниже полиномиальной сложности в общем случае ты не уйдёшь, потому что:

1. нужно хотя бы прочитать текст,
2. нужно извлечь события,
3. нужно посчитать частоты,
4. и, если паттернов много, сам вывод уже большой.

Но можно сделать задачу **FPT** по маленьким параметрам: длина цепочки, число типов действий, порог поддержки, top-k. Тогда сложность будет вида:

```text
f(k) * poly(n)
```

где `k` — маленький параметр, например максимальная длина цепочки.

## Что лучше сделать вместо текущего графа

Самый практичный вариант такой:

1. Из текста извлекать **действия** и **их аргументы**: verb, object, condition, result.
2. Нормализовать их в канонический вид: lemma + semantic role + domain entity.
3. Собрать из каждого документа **линию событий**.
4. На этих линиях запускать:

   * PrefixSpan,
   * SPADE,
   * closed/maximal sequential patterns,
   * контрастный анализ success/failure.

Так ты ищешь не “все зависимости в графе”, а **устойчивые сценарии действий**. Это и ближе к твоей бизнес-цели, и обычно значительно дешевле вычислительно.

## Что делать с “гарантированно приводит к цели”

Тут важна честность: из текста научных статей можно обычно получить **не гарантию**, а:

* высокий support,
* высокий confidence,
* сильную ассоциацию с outcome,
* контраст между успешными и неуспешными цепочками.

“Гарантированно” возможно только если у тебя есть строгая формальная модель процесса или дополнительные аксиомы. Иначе это будет не доказательство, а вероятностный вывод.

## Практический вывод

Да, задачу стоит пересмотреть.
Лучшее решение здесь — **не граф паттернов, а mining последовательностей событий**. Это уберёт большую часть комбинаторного взрыва и сохранит смысл задачи.
Текущий граф можно оставить только как промежуточное хранилище извлечённых сущностей и связей, но не как основной объект поиска.

Если нужно, следующим сообщением я могу предложить **конкретную новую архитектуру для “Карты Знаний”**: какие сущности извлекать, какой формат событий хранить и какой алгоритм mining выбрать под твои объёмы.

Предложи конкретную новую архитектуру для “Карты Знаний”

# 📊 4. Слой 3: Sequence Mining (ядро)

Теперь вместо графа — классическая задача:

> есть миллионы последовательностей → найти частые подпоследовательности

## Алгоритмы

### ✅ PrefixSpan (лучший старт)

* не генерирует кандидатов заранее
* работает на проекциях базы
* сильно быстрее brute-force

### Альтернативы:

* SPADE (если хочешь вертикальные представления)
* BIDE (если нужны closed patterns)

---

## Пример

```text
Doc1: A → B → C → D
Doc2: A → B → E
Doc3: A → C → D
```

Алгоритм найдёт:

```text
A → B   (часто)
A → C   (часто)
B → C   (реже)
```

👉 Без перебора всех путей как в графе

---

# ⚖️ 5. Добавляем SUCCESS / FAILURE

Это ключ к твоей цели.

Каждому документу добавляем label:

```python
Doc = {
    "sequence": [...],
    "outcome": "success" | "failure"
}
```

---

## Дальше считаем:

### 1. Support

```text
support(A → B) = 1200 документов
```

### 2. Confidence

```text
P(success | A → B)
```

### 3. Lift

```text
lift = P(success | pattern) / P(success)
```

---

## Это даёт:

### ✅ “успешные цепочки”

```text
extract → normalize → train
confidence = 0.91
```

### ❌ “тупиковые цепочки”

```text
extract → skip_normalization → train
confidence = 0.12
```

---

# 🚀 6. Почему это быстрее

### Было (граф):

```text
O(b^k)  ← ветвление по типам связей
```

### Стало (sequence mining):

```text
O(#patterns * avg_sequence_length)
```

👉 Нет повторного обхода одинаковых подграфов
👉 Нет взрыва из-за разных типов рёбер
👉 Нет path explosion
