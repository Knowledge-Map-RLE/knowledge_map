# Отчёт к §61. Реализация пайплайна преобразования статьи в Карту Знаний (Вариант A)

## Принятая архитектура в двух словах

Вариант A заменил прежнюю трёхуровневую цепочку одним детерминированным конвейером:

```
SourceRevision (исходный текст)
  → LinguisticProfile (токены, предложения S1..S895, секции)   [NLP-шлюз, модели не задеты]
  → структурные строки DSL  (один вызов LLM → 147 строк)        [SemanticGateway → cloud.ru]
  → ArticleBlock (материализация, provenance)                    [детерминировано]
  → Knowledge Map (узлы/рёбра)                                   [детерминировано]
  → Neo4j: ArticlePipelineRun · HAS_BLOCK · SOURCE_SPAN · IN_REVISION
```

Промежуточный семантический уровень в Варианте A **не используется**. Чанкинг отклонён пользователем: модель выдаёт до 384 000 выходных токенов, статья обрабатывается за **один вызов** (`execution.mode = "whole_article"`).

## 1. Какие файлы были изменены

- `api/infrastructure/article_pipeline.py` — `SemanticGateway`:
  - не-стриминг (`stream: False`) вместо SSE-обёртки ai-agent: чистые ошибки шлюза вместо обрыва соединения;
  - `reasoning_effort: "low"` (значение `"none"` cloud.ru отвергает HTTP 400 — это была первопричина «incomplete chunked read»);
  - убран `response_format/json_schema` — провайдер его не принуждает (probe показал: модель возвращает JSON, не соответствующий схеме);
  - нормализация ответа: JSON-обёртка `{"dsl": str}` если есть; иначе «сырой» текст ответа оборачивается в `{"dsl": content}`;
  - HTTP >= 400 → `OSError` с текстом ошибки провайдера.
- `knowledge_map_core/pipeline/knowledge_pipeline/dsl_rows.py` — парсер структурных строк:
  - приняты обе формы заголовка: код-мажор `B T<код> B<тег>` (канон) и реальный вывод модели — тег-мажор `B<тег> T<код>`;
  - неизвестные поля больше не валят прогон: сохраняются без потерь в `data["_extra"]`;
  - пустые ссылки (`[]`, `{}`, `-`, `none`, `n/a`, пустая строка) корректно вырождаются в «пусто».
- `knowledge_map_core/pipeline/knowledge_pipeline/knowledge_map_builder.py` — `_extra` исключён из display_text.
- `knowledge_map_core/pipeline/knowledge_pipeline/pipeline.py` — resume завершённой версии теперь быстрый путь (без повторного вызова LLM и без сброса `status`).
- `api/infrastructure/neo4j/article_pipeline_repository.py` — исправлен Cypher: `MATCH` перед `MERGE` для `SourceSpan IN_REVISION SourceRevision` (латентная ошибка, всплыла только на реальных данных).
- `api/tools/run_article_pipeline.py` — вынесена `finalize()`, добавлен флаг `--finalize` (повторная персистенция уже вычисленного результата, чей DB-save ранее упал).
- `api/.env.development` — `LLM_MAX_TOKENS=384000` (было 64000, недостаточно для 895 предложений).
- `ai/.env.development` — `AI_REQUEST_TIMEOUT=7200` (полные вызовы занимают 4–8 минут).

## 4. Какая каноническая модель выбрана

Промежуточная модель не выбрана — и это осознанное решение Variant A. Единственный источник для извлечения — source units статьи; лингвистический профиль сохраняет структуру источника, а семантические утверждения представляют структурные строки. Обратная совместимость с удалённым уровнем не поддерживается.

## 5. Какая каноническая модель структурных строк выбрана

DSL-строки вида `B T<код> B<тег> | key=value ... | unit=S<n>` (принимается и `B<тег> T<код>`). 54 типа (коды T1..T59) — из `TypesT`/`ALL_TYPES` в `shared/knowledge/knowledge_contracts`. Тег `B<тег>` — локальный идентификатор для ссылок (srcRef/tgtRef/ref/refs). Поля типов заданы `_spec`-словарём `block_dsl`.

## 6. Какая модель Concepts/Assertions выбрана

Отдельного уровня Concepts/Assertions нет. Карта Знаний строится напрямую из структурных строк (`build_knowledge_map`): узел = блок (instanceId, display_text из полей данных), `semantic_edges` — из relation/temporal_relation (source/target/relation), `dependency_edges` — отображение исходного порядка. Гарантия полноты: `validate_map` требует `set(nodes) == set(блоков)`.

## 7. Как реализован provenance

- В данных блока: `data["provenance"] = {"unit_ids": ["S<n>"], "source_spans": [{"revision_id", "start", "end"}]}`; спаны — из лингвистического профиля, вербатим выводится из `source.text + span` и **не дублируется** в `data` (поэтому у relation `data["source"]` свободно занимает текст сущности).
- В Neo4j: `ArticleBlock -[:SOURCE_SPAN]-> SourceSpan -[:IN_REVISION]-> SourceRevision`; uid спана = `sha256(source_id:start:end)`; одна пара «предложение» → один SourceSpan, разделяемый всеми блоками этого предложения (93 спана на 147 блоков).
- Проверки: `provenance_completeness=1.0`, spans валидируются границами предложений в `validate_structural`.

## 8. Как реализована связь между уровнями

Четыре уровня Variant A и их связь:
1. `SourceRevision` — исходный текст + `sha256` (детект изменений при применении).
2. `LinguisticProfile` — токены/предложения/секции; `unit=S<n>` привязывает строку к предложению.
3. `ArticleBlock` — материализация строк (instanceId, order, data, provenance); резюме-поток (`repo.apply`) переключает `active_pipeline_version` и переживает `HAS_BLOCK` с сохранением редакторского снапшота.
4. `Knowledge Map` — детерминированная деривация из блоков; payload на версии (`map_payload`).
В Neo4j связи: `Document→SourceRevision`, `Document→ArticlePipelineRun`, `ArticlePipelineRun→SOURCE→SourceRevision`, `ArticlePipelineRun→HAS_BLOCK→ArticleBlock→SOURCE_SPAN→SourceSpan→IN_REVISION→SourceRevision`.

## 9. Как реализована валидация

- Уровень контрактов: `validate_linguistic`, `validate_structural` (обязательные поля, unit, provenance-спаны), `validate_map` (полнота узлов, отсутствие самопетель, ацикличность визуальных зависимостей, non-empty display).
- Резюме-инварианты репозитория: `_validate_completed`, идемпотентность (completed-версии неизменяемы), контроль владельца документа, сверка `sha256` перед применением.
- Приёмка: `finalize()` — roundtrip `save→load==result`, идемпотентный save, повтор всех валидаций, сборка `report.json`.
- Quality-гейты: `gates.passed=true` (порог `semantic_token_fraction >= 0.1`), `automated_score=76.2`.

## 11. Какие проблемы остались

1. **Низкое покрытие** — `semantic_token_fraction=0.16`, 93/895 предложений. За один вызов модель выдала 147 строк на статью 108k символов; большая часть текста не представлена. Порог гейтов пройден, но семантическая полнота недостаточна.
2. **Связность** — 103/147 узлов-сирот (70%), 121 слабосвязная компонента; рёбра дают только 26 relation-строк. Карта «деревенская».
3. **Семантическое качество неверифицировано** — `semantic_fidelity=requires_review`; метрики precision/recall/F1 требуют золотого стандарта (референс `knowledge_map_assertions_acomys.md` — русский, источник и вывод — английский; прямое машинное сравнение некорректно, нужно ручное ревью).
4. **Модель не соблюдает схему** — `json_schema` провайдером не принуждается, модель всегда тратит `reasoning_tokens` (1.7k–17.9k на вызов), пишет поля вне вокабуляра (`detail` и пр., сейчас сохраняются в `_extra` без потерь, но не участвуют в модели).
5. **Скрытое reasoning** — `reasoning_effort:"none"` → HTTP 400 (448 ошибка); `"low"` уменьшает, но не убирает; это скрытые затраты без возможности отключить.
6. **Стоимость/латентность** — полный прогон 4–8 минут и 25–97k токенов; на 30M статей это неприемлемо без отбора и, вероятно, возврата к гибридной стратегии (§ отчёта по стоимости LLM vs NLP).
7. **Не детерминизм извлечения** — повторный вызов LLM даёт другой набор строк; нужен фикс-сид/повторные проходы или «извлечение подтверждено» на уровне продукта.
8. **Deduplication/atomicity** — `duplicate_fingerprint_candidates=0`, но переформулировки и атомарность утверждений требуют экспертной оценки.

Не скрываю: acceptance «зелёный» по инвариантам и определённым метрикам, но содержательное качество (покрытие, связность, faithful) — целенаправленно открытый результат, требующий ручной оценки и, вероятно, итерации промпта/модели.

## 12. Какие изменения были необходимы в документации или БД

**БД (Neo4j):**
- Введены unique-индексы на `uid` для `ArticlePipelineRun`, `SourceRevision`, `SourceSpan`, `ArticleBlock`.
- Перед созданием constraint выполнено **слияние 1500 legacy-дубликатов** `ArticleBlock` (uid `blk-*`; 38 886 узлов → 37 386 distinct; рёбра переключены на keeper). Без этого constraint на `uid` падал.
- Новая схема хранения Variant A: промежуточные семантические сущности и рёбра происхождения не создаются; блоки указывают на спаны напрямую.
