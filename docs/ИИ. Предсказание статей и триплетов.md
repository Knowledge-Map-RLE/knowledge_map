# ИИ. Предсказание статей и триплетов

Да. И я бы здесь разделил задачу на **две независимые задачи**:

1. **Prediction** — может ли Карта Знаний, имея только знания на момент времени `t`, правильно назвать статьи, которые появятся после `t`?
2. **Long-range prediction** — насколько далеко по графу находится реально предсказанная статья от исходной статьи/набора знаний?

При этом есть очень важная тонкость: **для оценки нельзя строить граф на всём датасете сразу**. Иначе алгоритм может случайно использовать информацию из будущего и получится утечка данных.

---

# 1. Что именно мы хотим проверить

Допустим, есть временная последовательность:

```text
2015  Article A
       ↓
2016  Article B
       ↓
2017  Article C
       ↓
2018  Article D
       ↓
2019  Article E
```

Статья `A` содержит:

```text
S1: A → утверждает → X
S2: X → активирует → Y
S3: Y → увеличивает → Z
```

Статья `B`:

```text
S4: B → подтверждает → S1
S5: B → обнаруживает → W
```

и т. д.

В 2015 году алгоритм должен увидеть **только граф, существовавший к концу 2015 года**.

И его задача:

> Какие статьи, появившиеся после 2015 года, с наибольшей вероятностью будут следующими важными продолжениями этого графа?

Например:

```text
Предсказание:

Article C — 0.81
Article D — 0.64
Article F — 0.51
```

А затем через некоторое время мы узнаём, что действительно вышли:

```text
Article C
Article D
```

Получаем проверяемый результат.

---

# 2. Но я бы не предсказывал статью непосредственно

Это, пожалуй, самое важное изменение, которое я бы предложил.

Не:

```text
Article A → Article C
```

а:

```text
Article A
   ↓
утверждения A
   ↓
паттерн
   ↓
предсказанные утверждения
   ↓
статьи, которые могли бы проверить/получить эти утверждения
```

То есть сначала алгоритм должен предсказывать **следующий участок пространства знаний**, а уже потом искать статьи, соответствующие этому участку.

Например:

```text
A:

protein X → activates → pathway Y

B:

pathway Y → increases → inflammation

```

Карта может обнаружить паттерн:

```text
X → activates → Y
Y → increases → inflammation
```

и предсказать:

```text
X → contributes to → inflammation
```

А затем посмотреть:

> Какая будущая статья фактически получила такой результат?

Это гораздо ближе к твоей идее **«предсказать следующий эксперимент»**, чем обычный recommendation engine.

---

# 3. Нужно формализовать статью как множество утверждений

Для статьи `A`:

```text
A = {S1, S2, S3, ..., Sn}
```

где:

```text
S = (subject, predicate, object)
```

Но в твоей системе этого недостаточно, потому что есть метаутверждения.

Например:

```text
S1:
A → утверждает → S2

S3:
Experiment1 → подтверждает → S2

S4:
Experiment1 → опровергает → S5
```

Поэтому фактически статья представляет собой **подграф утверждений**:

```text
Article
   │
   ├── S1
   │    └── S7
   │         └── S12
   │
   ├── S2
   ├── S3
   │    └── S9
   └── S4
```

И именно этот подграф нужно сравнивать между статьями.

---

# 4. Первый фундаментальный алгоритм — нормализация утверждений

Прежде чем искать паттерны, нужно решить проблему:

```text
A → активирует → B
```

и

```text
B is activated by A
```

не должны считаться разными знаниями.

Поэтому нужен канонический вид:

```text
subject = A
predicate = activates
object = B
```

То же касается:

```text
dopamine
Dopamine
DA
3-hydroxytyramine
```

Если это одна сущность, они должны разрешаться в одну canonical entity.

То есть нужен слой:

```text
Raw statement
      ↓
Entity resolution
      ↓
Predicate normalization
      ↓
Canonical statement
```

И только после этого сравнивать статьи.

---

# 5. Второй алгоритм — Statement Similarity

Теперь можно определить:

> Насколько утверждение из статьи A похоже на утверждение из статьи B?

Самый простой вариант:

```text
sim(S1, S2) =
    совпадает субъект
    +
    совпадает предикат
    +
    совпадает объект
```

Например:

```text
S1:
p53 → activates → apoptosis

S2:
p53 → activates → apoptosis
```

```text
similarity = 1.0
```

А:

```text
S1:
p53 → activates → apoptosis

S2:
p53 → inhibits → apoptosis
```

уже:

```text
subject: same
predicate: different
object: same
```

Например:

```text
similarity = 0.67
```

Но здесь появляется очень интересная возможность.

Для твоей системы я бы использовал **структурную similarity**, которая учитывает не только сам триплет, но и его подграф.

---

# 6. Сравнивать нужно не только триплет, а его «контекст»

Допустим:

```text
S1:
A → activates → B
```

В одной статье вокруг него:

```text
C → activates → A
A → activates → B
B → increases → D
```

В другой:

```text
X → inhibits → A
A → activates → B
B → increases → D
```

Само утверждение одинаковое.

Но **структура контекста разная**.

Можно определить:

```text
Neighborhood(S)
```

например на расстоянии `k=2`.

Тогда:

```text
Similarity(S1, S2)
=
similarity(
    canonical statement,
    local statement neighborhood
)
```

Это уже намного более сильный механизм.

# 8. Здесь можно начать без нейросетей

И это очень хорошо соответствует твоему эксперименту.

Можно сделать **rule-based prediction engine**.

Например правило:

```text
ЕСЛИ

A → activates → B
B → activates → C

ТО

кандидат:
A → activates → C
```

Другой паттерн:

```text
A → inhibits → B
B → activates → C

⇒

A → affects → C
```

Но лучше не придумывать произвольные биологические правила.

Пусть правила будут основаны на **исторически обнаруженных паттернах**.

# 9. Mining исторических паттернов

Вот здесь, на мой взгляд, начинается настоящая проверка твоей гипотезы.

Берём старую часть корпуса:

```text
2000–2015
```

и ищем:

```text
паттерн X
    ↓
через 1–5 лет
    ↓
паттерн Y
```

Например:

```text
P1:

A → activates → B

P2:

B → increases → C

```

часто оказывается перед:

```text
P3:

A → increases → C
```

Тогда система запоминает:

```text
P1 + P2
      ↓
P3
```

с некоторой статистикой:

```text

occurrences = 184
successes = 91
precision = 49.5%
```

И это уже **настоящий научный паттерн**, извлечённый из истории литературы.

# 11. Теперь проблема библиографических ссылок

Ты правильно отметил:

> DAG строится не только по зависимости утверждений, но и по библиографическим ссылкам.

Здесь я бы **не смешивал разные типы ребер** в одно.

Например:

```text
Article A ──cites──> Article B
```

это совершенно не то же самое, что:

```text
S1 ──supports──> S2
```

И не то же самое, что:

```text
S1 ──causes──> S2
```

Поэтому граф должен быть **typed DAG / multi-relational graph**.

Например:

```text
Article
   │
   ├── contains ──> Statement
   │
   ├── cites ─────> Article
   │
   └── reports ───> Experiment

Statement
   │
   ├── supports ──> Statement
   ├── contradicts ──> Statement
   ├── causes ─────> Statement
   └── depends_on ─> Statement
```

# 17. Метрика №1 — насколько хорошо предсказываем

Здесь можно использовать обычные ranking metrics.

Например:

### Precision@K

Из первых 10 предсказаний:

```text
10 predictions
3 реально появились
```

получаем:

```text
Precision@10 = 0.3
```

### Recall@K

Если среди всех релевантных будущих статей было 20:

```text
нашли 3
```

то:

```text
Recall@10 = 3 / 20
```

### MRR

Если правильная статья впервые появляется на позиции:

```text
5
```

то:

```text
MRR = 1/5 = 0.2
```

### NDCG@K

Очень полезна, если у тебя есть **степень релевантности**, а не просто:

```text
правильно / неправильно
```

# 18. Но твоя идея требует второй метрики

И вот здесь становится интереснее.

Для каждого successful prediction:

```text
A → predicted Article Z
```

вычисляем:

```text
D(A,Z)
```

Получаем:

```text
prediction     rank     hit     distance
------------------------------------------------
Z              1        ✓       17
X              2        ✓       5
Q              3        ✗       -
Y              4        ✓       11
```

Тогда можно определить:

### Mean Successful Prediction Distance

```text
MSPD =
Σ distance(successful predictions)
/
number of successful predictions
```

Например:

```text
(17 + 5 + 11) / 3 = 11
```

```text
Which Article contains them?
```

Это устранит огромное количество шума.

---

## Я бы сформулировал два главных KPI Карты Знаний так

### KPI-1 — Predictive Accuracy

> **Доля действительно появившихся в будущем релевантных утверждений/статей, которые система смогла предсказать по состоянию графа на момент времени `T`.**

Измеряется через:

```text
Precision@K
Recall@K
MRR
NDCG@K
```

### KPI-2 — Predictive Distance

> **Топологическое расстояние в историческом графе между состоянием знаний, из которого было сделано предсказание, и фактически появившимся предсказанным знанием.**

И здесь я бы обязательно фиксировал **snapshot времени**, чтобы расстояние не использовало информацию из будущего.

---

И тогда появляется очень красивая формулировка всей идеи Карты Знаний:

> **Система должна извлекать из научной литературы структуру знаний, обнаруживать исторические паттерны перехода от одних утверждений к другим и на основе состояния графа в момент `T` предсказывать ещё не появившиеся знания, причём желательно предсказывать их с высокой точностью и на большом топологическом и временном расстоянии.**

Это уже можно превратить в **строго воспроизводимый benchmark для Карты Знаний**, а не просто в субъективное утверждение, что «граф выглядит полезным».

И, на мой взгляд, **именно сейчас имеет смысл остановиться на разработке промпта извлечения утверждений**: качество canonical statements, сущностей, предикатов, метаутверждений и временного/экспериментального контекста будет непосредственно определять потолок этого benchmark.
