# Карта Знаний. План пайплайна: статья → структурные строки → DAG

Дата: 2026-09-19

## Исходные решения

- Пайплайн: **текст научной статьи → структурные строки → DAG карты знаний**. Промежуточный семантический слой исключён как лишний.
- Для каждого этапа создаются **эталоны** (gold standard) и **метрики**. Цель — чтобы человек или машина могли идти по DAG к целям, например «продлить жизнь».
- Эталонный набор: **20 статей**.
- Модель этапа 1: **deepseek-ai/DeepSeek-V4-Flash** от cloud.ru. Локальная Qwen не используется.
- Все промпты и результаты LLM на английском, исходный текст статьи не меняется.

Допущение о DAG, которое нужно подтвердить, описано в разделе 2 (пункт 1).

---

## 1. Архитектура

```text
Статья (MD, каноничная ревизия)
   │  Этап 0: подготовка источника (код)
   ▼
Пронумерованные предложения + индекс диапазонов
   │  Этап 1: LLM + валидаторы
   ▼
Структурные строки (типизированные блоки + триплеты внутри, provenance)
   │  Этап 2: код (blockConverter, разрешение сущностей, построение рёбер) + валидаторы
   ▼
Реестр Concept/Assertion → DAG карты знаний → display text
```

### Что берём из задачи для Codex

- английский как канонический язык, исходный текст неизменен;
- Concept ≠ Assertion, типизированные ссылки (`@C`, `@A`, литерал), атомарность утверждений;
- статус `hypothesized` по умолчанию;
- сохранение модальности, отрицания, сравнения, причинности и контекста;
- запрет внешних знаний, разделение извлечения и логического вывода;
- LLM не создаёт UUID и не пишет в БД, это делает код;
- валидатор после каждого этапа;
- сквозная трассируемость и provenance отдельно от текста триплета;
- сквозной тест «статья → БД → загрузка → display text»;
- журнал конфликтов документации и итоговый отчёт.

### Что выбрасываем

Все разделы прежней задачи, описывавшие промежуточный семантический слой, удалены или заменены прямым маршрутом.

Новая цепочка трассировки:

```text
узел DAG → Assertion → структурная строка → предложения и диапазон символов → ревизия статьи
```

Роль «не терять информацию» берут на себя два механизма:

1. покрытие на уровне предложений (эталон размечает, какое знание несёт каждое предложение);
2. обратная генерация текста из DAG для проверки потерь.

### Как получаем provenance

LLM ненадёжно считает символьные диапазоны. Поэтому на этапе 0 код нумерует предложения и даёт им ID. LLM возвращает только ID предложений-источников, а точные диапазоны символов вычисляет код.

## 2. Что решить до старта (противоречия в документах)

1. **Что такое «DAG».** Предлагается разделить связи на два вида:
   - *смысловые* (`inhibits`, `causes`, ссылки на утверждения), они могут быть циклическими из-за обратных связей в биологии;
   - *зависимости*, подмножество рёбер «A нужно или подтверждает B» (цель ← гипотеза ← предпосылки, эксперимент → находка → утверждение). Этот слой обязан быть ацикличным, по нему идёт навигация к цели.

   Ссылка одного утверждения на другое не создаёт ребро автоматически (правило 29 из задачи Codex). Это главное решение: от него зависит эталон этапа 2.
2. **Что такое «структурная строка».** В спецификации это типизированный блок (`finding`, `relation` и т. д.), в задаче Codex это «Concepts + Assertions». Предлагается считать канонической спецификацию: блок содержит триплеты, а реестр Concept/Assertion строится из блоков кодом.
3. **Provenance в спецификации** ссылается только на ID предложений и диапазоны ревизии.
4. **Правила 5–6 против 65–66 и 71** в правилах преобразования. Старые оставляют длинную фразу одним Subject, новые требуют дробить. Предлагается принять новые: составной концепт остаётся одним узлом, а его внутренняя структура хранится явными `is_a` / `has_state`-утверждениями.
5. **Закрытый список предикатов в `claim`** (спецификация) против открытых нормализованных предикатов (правила). Нужен реестр предикатов с классами: таксономические, причинные, ассоциативные, сравнительные, методологические. Классы нужны и метрикам («ассоциация → причинность» считается критической ошибкой), и навигации по DAG.
6. **Термины.** Блок `claim`, Assertion, Statement и Claim из архитектуры Proposition/Claim/Evidence (план реализации) пересекаются. Нужен единый глоссарий.
7. **Приоритеты по типам блоков.** Реестр содержит 52 типа. Предлагаемые уровни:
   - **A**, без чего DAG не строится: `goal`, `hypothesis`, `prerequisite`, `experiment`, `experiment_step`, `intervention`, `animal_group`, `finding`, `claim`, `relation`, `temporal_relation`, `open_questions`, `limitations`, `link_with_aging`;
   - **B**, качество доказательств: `sample_size`, `probability_value`, `effect_size`, `confidence_interval`, `research_design`;
   - **C**, остальное: метаданные, `image`, `code`, `funding` и т. д.

   Метрики взвешиваются по уровням.

## 3. Эталоны

### Принципы

- **Эталон проектируется от цели.** Сначала формулируются вопросы, на которые DAG должен отвечать (competency questions): «какие вмешательства связаны со снижением фиброза и какова цепочка доказательств?», «что должно быть верно, чтобы гипотеза имела смысл?», «что не проверено или неизвестно?». Эталоны этапов выводятся из этих вопросов.
- **Три уровня качества:**
  - *Gold*: разметка человеком с проверкой, на ней считаются метрики;
  - *Silver*: черновик сильной LLM с выборочной проверкой, для быстрых регрессий;
  - *Bronze*: полностью автоматический результат, только для мониторинга.
- **Dev и замороженный test.** Промпты подбираются на dev, test не открывается до финальной оценки. Примеры из test не попадают в few-shot.
- **Эталон допускает несколько верных ответов:** классы эквивалентности предикатов и синонимов концептов, альтернативные декомпозиции одной фразы. Строго проверяются только инварианты: отрицание, модальность, направление сравнения, числа с единицами.
- **Единое версионируемое руководство разметчика** из сведённых правил с разобранными спорными случаями. Расхождения между разметчиками ведут к правке руководства.
- **Разметка в редакторе Языка Знаний.** Формат «нового формата статей» и есть формат эталона.
- **Черновик от LLM другого семейства, чем генератор.** Разметка «LLM → человек» быстрее ручной, но создаёт эффект привязки. Чтобы измерить его, на части статей делается слепой проход без черновика.

### Набор из 20 статей

- **10 dev** (включая статью про Acomys) и **10 замороженных test**.
- Стратификация по типам исследований из `research_design` (оригинальное, клиническое, обзор, систематический обзор, мета-анализ, case report), по языку (русские и английские), по организму, по доле Results и Discussion.
- Отдельный набор «тяжёлых случаев»: отрицание, сравнения, модальность, координации, вложенные утверждения, числа с единицами.
- Часть статей (например, 5 из 20) размечается двумя людьми или двумя проходами одного человека с паузой, чтобы измерить согласие и потолок качества.
- Существующий файл с утверждениями по Acomys используется как затравка, но перепроверяется: он создан до новых правил 65+.

| Этап | Эталон | Объём |

## 4. Метрики

Метрики двух типов:

- **ворота**: 100% или 0, иначе результат не идёт дальше; эталон не нужен;
- **оценочные**: считаются по эталону.

| Этап | Ворота (без эталона) | Оценочные метрики |
|---|---|---|
| 0 | Каждый диапазон возвращает точную цитату из ревизии | F1 сегментации, точность определения разделов, сохранность чисел, единиц и таблиц |
| 1 | Валидность схемы, уникальные ID, `metadata` не более одного раза, ссылки разрешаются и типизированы, арность предикатов, есть provenance, английский язык, статус `hypothesized`, нет provenance внутри Subject/Predicate/Object | P/R/F1 типов блоков (отдельно по уровням A/B/C); точность полей (DOI, числа с единицами, n, p-value); P/R/F1 триплетов на трёх уровнях строгости: нормализованное совпадение, совпадение концептов, семантическое (embedding + LLM-судья) |
| 1, точность смысла | — | Доля сохранённых отрицаний и модальностей; матрица «ассоциация / причинность» (повышение до причинности — критическая ошибка); направление и обе стороны сравнения; сохранение контекста (возраст, вид, условия); доля утверждений с ровно одним отношением |
| 1, достоверность | — | Доля утверждений, подтверждённых своим предложением-источником (энтейлмент); утечка внешних знаний; число критических ошибок на 100 утверждений (выдумка, усиление, переворот отрицания или направления) |
| 1, полнота | — | Покрытие знаниевых предложений (с весом на Results и Discussion); полнота блоков уровня A; захват неизвестного и ограничений |
| 1, концепты | — | Повторное использование одного концепта в статье; ошибки слияния разных контекстов (ген, белок, экспрессия); ошибки недослияния |
| 1, устойчивость | — | Согласованность между запусками; стоимость и задержка на статью; калибровка флагов неуверенности (доля ошибок среди помеченных против непомеченных) |
| 2 | Ацикличность слоя зависимостей, нет висячих ссылок и узлов без provenance, каждый узел читается человеком без UUID, все ссылки типизированы | P/R/F1 рёбер по типам; ошибки направления рёбер; доля ложных зависимостей из простых ссылок; кластерный F1 сущностей (B-cubed) |
| 2, навигация | — | Достижимость целей: доля эталонных вмешательств и экспериментов, достижимых от цели; полнота эталонных путей; корректность найденных путей (нет прохода по ассоциативным рёбрам как по причинным); **доля пройденных competency questions** — ключевая метрика этапа |
| 2, эпистемика | — | Все выведенные утверждения помечены как выведенные и `hypothesized`; точность вывода по `is_a`; сохранность слабейшего статуса вдоль пути |
| 2, потери | — | Обратная генерация текста из DAG: доля эталонных ключевых фактов, восстановимых из этого текста, и доля верных ответов на вопросы по статье |
| Сквозные | — | Трассировка: выборка узлов проходит путь назад до текста, каждый шаг подтверждён; каскад ошибок (качество этапа 2 на эталонном входе против входа этапа 1) |

### Как отчитываться

- **Асимметричная оценка ошибок.** Усиление, выдумка, переворот направления или отрицания намного тяжелее пропуска (правило «минимального усиления»).
- **Доверительные интервалы бутстрэпом по статьям**, а не по утверждениям: утверждения одной статьи коррелированы. На 10 dev и 10 test статьях детектируются только крупные различия, поэтому мелкие улучшения проверять на минимальных парах и на уровне предложений.
- **Версионирование отчётов** по четвёрке «модель + версия промпта + версия схемы + версия руководства». Версию DeepSeek-V4-Flash у провайдера фиксировать и прогонять регрессию при её смене.
- **Пороги фиксировать после базового замера**, а не заранее.
- **LLM-судья должен быть сильнее генератора и другого семейства.** Перед массовым использованием проверить его согласие с человеком на подвыборке эталона. Черновики silver-разметки тоже делать не той моделью, которую оцениваем.

## 5. Порядок работ

1. **Решения и словарь.** Закрыть пункты раздела 2, обновить спецификацию, свести руководство разметчика, завести реестр предикатов и глоссарий.
2. **Детерминированный фундамент.** Этап 0, схемы, валидаторы-ворота, ID кодом. Метрики-ворота уже работают без эталона.
3. **Эталон v0 на одной статье** (Acomys): блоки, разметка по предложениям, эталонный DAG, competency questions. Обкатывается процесс, уточняется руководство.
4. **Оценочный стенд.** Запуск конвейера на dev, вычисление метрик, отчёты по версиям, регрессионные ворота в CI (pytest), интерфейс просмотра результатов.
5. **Этап 1 на DeepSeek-V4-Flash.** Английские промпты, разбиение по разделам, строгий JSON-вывод, базовый замер на dev. Сравнить со старшей моделью, чтобы понять, где Flash недотягивает, и решить, нужна ли маршрутизация по сложности блоков.
6. **Этап 2.** blockConverter, разрешение сущностей внутри статьи, правила построения рёбер зависимостей, проверки, display text, обратная генерация текста.
7. **Расширение эталона** до 20 статей, двойная разметка подвыборки, замораживание test, калибровка порогов.
8. **Сквозной тест и отчёт** по форме из задачи Codex.
9. **Потом, не в первой итерации:** склейка знаний между статьями (Proposition / Claim / Evidence из плана), декомпозиция целей, поиск паттернов. Точки расширения закладываются сразу: стабильные ID, реестр концептов и предикатов, `link_with_aging`.

## 6. Главные риски

- **Циклы.** Обратные связи в биологии нарушат ацикличность. Нужна политика: выделять зависимостные рёбра отдельно и разворачивать петли во времени, а не молча удалять.
- **Качество Flash на блоках уровня A.** Проверяется базовым замером на dev. Если сложные блоки (`finding`, `relation`, `hypothesis` с опровержением) дают критические ошибки, вводится маршрутизация: простые блоки Flash, сложные более сильной моделью.
- **Смена версии модели у провайдера.** Результаты могут дрейфовать без изменений в коде. Защита: фиксация версии, регрессия на dev и минимальных парах.
- **Дороговизна эталона.** Порядок экономии: сначала инварианты и минимальные пары, затем competency questions, полный DAG в последнюю очередь.
- **Дрейф руководства.** Каждая правка правил сопровождается перепрогоном эталона и записью в журнале изменений.
