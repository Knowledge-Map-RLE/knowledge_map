# ИИ. Как строить Связи

Ещё дело в том что нужно визуализировать граф (карту) знаний из блоков, где блок содержит одно зарезолвенное утверждение. Этот граф тоже DAG и он должен органично по смыслу выстраивать цепочки утверждений, какое зависит от какого, что бы достичь какой то цели, то есть это визуальное отображение механизма достижения цели через промежуточные задачи (блоки-утверждения). И сейчас проблема текущей визуализации которую я уже сделал, это то что блоки отображаются с множеством лишних связей из-за наличия идентификаторов. Но где я ошибся что бы убрать побочные связи, я не знаю.

---

Именно. Теперь я вижу, где, скорее всего, находится ошибка. И она, похоже, **не в UUID как таковых**, а в том, что мы используем одну и ту же структуру ссылок сразу для двух разных задач:

1. **семантически выразить утверждение и сделать его рекурсивно разрешаемым**;
2. **построить визуальный DAG достижения цели**.

Эти графы **не обязаны совпадать**.

### Что, вероятно, сейчас происходит

Допустим, есть:

```text
A1:
Rapamycin → reduces → Inflammation

A2:
A1 → supportedBy → Study123

A3:
Study123 → uses → Mouse

A4:
A1 → contradicts → A5
```

Если визуализатор увидит все ссылки между ресурсами, он может построить:

```text
A1 ──→ A2
│
├────→ Study123
│
├────→ Mouse
│
└────→ A5
```

Хотя для твоей **карты механизма достижения цели** тебе, возможно, вообще не нужны эти связи.

Тебе нужен другой граф:

```text
Goal
  ↓
A7
  ↓
A3
  ↓
A1
```

где стрелка означает не просто:

> «в assertion содержится ссылка на X»

а:

> **«для выполнения/обоснования этого утверждения нужен следующий блок утверждения».**

Это совершенно другой тип отношения.

---

# Самая важная идея

Я бы разделил:

## 1. Assertion Graph

Это **семантический граф ссылок**.

Например:

```text
A3 → references → A1
A2 → references → Study123
A4 → references → A1
```

Он нужен для хранения и резолва.

## 2. Knowledge Map Graph

Это **граф зависимостей для достижения цели**.

Например:

```text
A1 → enables → A2
A2 → enables → A3
A3 → achieves → Goal
```

Именно его ты визуализируешь блоками.

И **второй граф нельзя автоматически строить просто как все ссылки первого графа**.

Вот, думаю, здесь мы раньше и ошиблись.

---

# Почему UUID сам по себе не является причиной лишних связей

Представим:

```text
A1 = E1 → P1 → E2
```

и:

```text
A2 = A1 → P2 → E3
```

При резолве `A2` получится что-то вроде:

```text
A1
└── E1 → P1 → E2
      ↓
      P2 → E3
```

Если затем твой визуализатор смотрит на **каждую ссылку между объектами**, он видит множество отношений.

Но тебе нужен **один блок `A2`**, содержащий зарезолвленное утверждение:

```text
[E1 → P1 → E2] → P2 → E3
```

То есть внутренние ссылки, использованные для построения текста блока, **не должны автоматически становиться рёбрами между блоками**.

Это очень важный момент.

---

# Представь блок как чёрный ящик

Например блок:

```text
┌────────────────────────────────────┐
│ B7                                 │
│                                    │
│ Rapamycin reduces inflammation     │
└────────────────────────────────────┘
```

Внутри него может быть:

```text
Rapamycin
Inflammation
reduces
```

и каждый элемент имеет свои ID.

Но визуальный DAG **не должен поэтому соединять B7 с блоками Rapamycin, Inflammation, reduces**.

Это просто внутренняя структура содержимого блока.

Для визуального DAG важно только:

```text
B3 ─────→ B7
```

если **B3 действительно является зависимостью B7**.

---

# Значит, нам нужен критерий: что такое зависимость?

Вот это я бы теперь определил абсолютно формально.

Для двух assertion:

```text
A
B
```

стрелка:

```text
A → B
```

существует не тогда, когда `B` содержит UUID `A`.

А когда выполняется специальное семантическое условие:

> **B использует результат/смысл A как необходимую часть своего собственного утверждения или действия по достижению цели.**

И это уже не просто reference.

---

# Например

Пусть:

```text
A1:
mTOR activation increases autophagy
```

```text
A2:
Rapamycin inhibits mTOR
```

```text
A3:
Rapamycin increases autophagy
```

В обычном assertion graph:

```text
A3
может ссылаться на
A1
A2
```

Но для Knowledge Map:

```text
A2
  ↓
A3
```

может быть полезной причинной/логической зависимостью.

А:

```text
A3 → citedBy → Paper123
```

вообще не является шагом механизма.

То есть:

```text
references ≠ dependency
```

И это, вероятно, **ключевая ошибка текущей визуализации**.

---

# Я бы поэтому ввёл два совершенно разных вида связи

### Семантическая ссылка

Она нужна для структуры assertion:

```text
A2
  subject = A1
  predicate = supports
  object = Study123
```

Она отвечает:

> «Что на что ссылается?»

### Dependency edge

Отдельно:

```text
A1 ──depends-on──→ A2
```

Она отвечает:

> «Какие блоки нужны друг другу в механизме достижения цели?»

И именно **dependency edge** должен использоваться для построения визуальной карты.

---

# Причём dependency edge вообще может отсутствовать в исходном утверждении

Это очень важно.

Например:

```text
A1:
Rapamycin inhibits mTOR.

A2:
Inhibition of mTOR increases autophagy.
```

Сами assertions не обязательно должны содержать:

```text
A2 → dependsOn → A1
```

Но **анализатор карты** может вывести:

```text
A1 → A2
```

потому что:

```text
result(A1)
    matches
condition(A2)
```

То есть визуальная карта может быть **вычисляемым графом**, а не просто графом хранимых ссылок.

И это, на мой взгляд, гораздо ближе к твоей изначальной идее Карты Знаний.

---

# Тогда у нас получается три уровня

### Уровень 1. Содержание

```text
A1 = E1 → P1 → E2
```

### Уровень 2. Ссылки / provenance / meta-assertions

```text
A2 = A1 → supportedBy → Study123
A3 = A1 → contradictedBy → A4
```

### Уровень 3. Goal DAG

```text
Goal
 ↑
A7
 ↑
A5
 ↑
A1
```

И **уровень 3 — это не просто резолв уровня 2**.

Это отдельный вычисляемый слой.

---

# Тогда я бы пересмотрел твой AST/DAG

То, что ты называешь AST, действительно может понадобиться для:

```text
resolve(A)
```

Например:

```text
A7
├── subject → A3
│             ├── subject → A1
│             └── object  → E2
└── object → A6
```

Это структура **одного зарезолвленного assertion**.

Но визуальная карта:

```text
A1 → A3 → A7 → Goal
```

— это уже **dependency DAG**.

Поэтому я бы не пытался одним графом решить обе задачи.

---

# А вот где UUID начинают приносить пользу

UUID тогда остаются очень полезными.

Например:

```text
A17
```

может участвовать одновременно в:

```text
resolve(A22)
resolve(A31)
dependency(A44, A17)
provenance(A53, A17)
```

И при этом его внутренние ссылки не загрязняют визуальный DAG.

То есть:

> **UUID не создают лишние визуальные связи. Лишние связи создаёт правило построения визуального графа, если оно трактует каждую ссылку как dependency edge.**

Это, думаю, наиболее вероятный источник твоей проблемы.

---

# Я бы даже предложил изменить название

Не считать:

```text
Graph = все связи между assertions
```

а сделать:

```text
Knowledge Graph
      ↓
Semantic Graph

Knowledge Map
      ↓
Dependency Graph
```

**Knowledge Graph** отвечает:

> Что с чем связано?

**Knowledge Map** отвечает:

> Какая последовательность утверждений ведёт нас к цели?

И вот второе — это то, что ты визуализируешь блоками.

---

# И ещё один очень важный момент: одно утверждение может содержать несколько потенциальных зависимостей

Например:

```text
A10:
Rapamycin inhibits mTOR and thereby increases autophagy.
```

Это может быть лучше разложено на:

```text
A1:
Rapamycin inhibits mTOR.

A2:
mTOR inhibition increases autophagy.

A3:
A1 + A2 → Rapamycin increases autophagy.
```

Тогда карта становится:

```text
A1 ──┐
     ├──→ A3
A2 ──┘
```

Это уже очень интересная модель **AND-зависимостей**.

А если:

```text
A4 OR A5
```

дают один и тот же результат, нужна уже альтернативная зависимость.

То есть в будущем твоя карта может стать не просто DAG, а **логическим DAG**:

```text
AND
OR
```

И именно это позволит действительно выстраивать **механизм достижения цели**, а не просто показывать связанные утверждения.

---

## Поэтому я бы сейчас зафиксировал главное архитектурное правило

> **Не строить визуальную Карту Знаний напрямую из ссылок subject/object.**

Сначала:

```text
Assertions
    ↓
resolve references
    ↓
Semantic representation
    ↓
infer / define dependencies
    ↓
Dependency DAG
    ↓
visual blocks
```

А блок содержит:

```text
один assertion
+
его полностью зарезолвленное представление
```

но его связи с другими блоками определяются **отдельной логикой зависимости**, а не наличием UUID в его тексте.

Это, на мой взгляд, гораздо ближе к той системе, которую ты изначально хотел построить.

И поскольку ты уже сделал визуализатор, очень полезно увидеть **конкретно тот граф, который сейчас получается**: по нему я смогу показать, какие именно связи являются ложными и какое правило их порождает.

---

Понятно. Я действительно строил визуализацию из ссылок subject/object. Но как тогда мне технически получать связи для блоков? Достаточно будет какого то алгоритма над утверждениями или придётся использовать дорогую нейросеть?

---

Да — и вот здесь я бы **не начинал с дорогой нейросети**. Для первой рабочей версии связи между блоками вполне можно получать алгоритмически, а нейросеть использовать только там, где формальных правил недостаточно.

Более того, я бы разделил задачу на **два этапа: candidate dependencies и semantic verification**.

### 1. Сначала дешёвый алгоритм строит кандидатов

Пусть у нас есть утверждения:

```text
A1: Rapamycin → inhibits → mTOR
A2: mTOR inhibition → increases → autophagy
A3: autophagy → reduces → cellular damage
A4: Rapamycin → increases → lifespan
```

Алгоритм смотрит не на UUID, а на **семантическую структуру триплетов**.

Например:

```text
A1:
Rapamycin → inhibits → mTOR

A2:
mTOR inhibition → increases → autophagy
```

Может заметить совпадение:

```text
A1.object = mTOR
A2.subject = mTOR inhibition
```

и создать кандидат:

```text
A1 → A2
```

Но тут уже видно, что простого совпадения UUID недостаточно. Нужно понимать, что:

```text
mTOR
```

и

```text
mTOR inhibition
```

находятся в некотором отношении.

Поэтому я бы ввёл несколько уровней сопоставления.

---

# 2. Уровень 1 — точное структурное совпадение

Самый дешёвый случай.

```text
A1: X → produces → Y
A2: Y → causes → Z
```

Здесь очевидный кандидат:

```text
A1 → A2
```

Потому что результат `A1` является входом `A2`.

Это можно делать обычными индексами в Neo4j/другом хранилище.

---

# 3. Уровень 2 — совпадение через разрешённые отношения

Например:

```text
A1:
Rapamycin → inhibits → mTOR

A2:
mTOR inhibition → increases → Autophagy
```

Здесь уже нужна **маленькая формальная семантика predicates**.

Например система знает:

```text
inhibits(X, Y)
```

создаёт состояние:

```text
inhibited(Y, X)
```

и понимает, что:

```text
mTOR inhibition
```

может быть следствием:

```text
Rapamycin inhibits mTOR
```

Это уже можно делать правилами.

И это очень перспективный путь, потому что таких правил можно постепенно накапливать.

---

# 4. Уровень 3 — композиция утверждений

Например:

```text
A1:
X → inhibits → Y

A2:
Y → activates → Z

A3:
X → inhibits → Z
```

Алгоритм может проверить, существует ли известное правило композиции:

```text
inhibits + activates → inhibits
```

И тогда получить:

```text
A1 + A2 ⇒ candidate A3
```

Но тут очень важно не превратить эвристику в «истину».

Поэтому я бы хранил:

```text
derivedDependency = true
confidence = ...
rule = ...
```

---

# 5. И вот здесь появляется действительно важная архитектура

Я бы сделал не один алгоритм, а **двухступенчатый pipeline**.

```text
Assertions
   ↓
Candidate Generator
   ↓
100–10000 потенциальных связей
   ↓
Semantic Verifier
   ↓
10–100 настоящих dependency edges
   ↓
Knowledge Map DAG
```

Candidate Generator должен быть очень дешёвым.

Semantic Verifier уже может использовать:

* правила;
* similarity;
* LLM.

Причём **LLM не должен смотреть все пары утверждений**. Это будет катастрофически дорого.

---

# 6. Основной критерий для связи должен быть не «похожи ли два утверждения»

Это очень важно.

Нужно проверять:

> Может ли результат A быть использован как условие, механизм, доказательство или промежуточный результат B?

То есть:

```text
A → B
```

не означает:

```text
similarity(A, B) > threshold
```

Например:

```text
A:
Rapamycin inhibits mTOR.

B:
Rapamycin is widely used in research.
```

Они семантически очень близки.

Но:

```text
A → B
```

как dependency — бессмысленно.

Поэтому cosine similarity может быть только **генератором кандидатов**, но не финальным решением.

---

# 7. Я бы ввёл несколько классов dependency

Это очень поможет алгоритму.

Например:

```text
causal
logical
mechanistic
evidential
temporal
conditional
definitional
```

И ещё более интересный класс:

```text
goal-directed dependency
```

Например:

```text
A1 → target → A2
```

не обязательно означает, что A1 причинно вызывает A2.

Это означает:

> Для достижения состояния, описанного A2, нам нужно состояние/результат A1.

И именно это тебе нужно для визуальной Карты Знаний.

---

# 8. Представим цель

```text
G:
Increase healthy human lifespan
```

И assertions:

```text
A1:
Rapamycin inhibits mTOR

A2:
mTOR inhibition increases autophagy

A3:
Autophagy reduces cellular damage

A4:
Reduced cellular damage improves tissue function

A5:
Improved tissue function increases healthspan
```

Тогда система может построить:

```text
A1
 ↓
A2
 ↓
A3
 ↓
A4
 ↓
A5
 ↓
G
```

Причём **каждую стрелку не обязательно получать нейросетью**.

Можно получить:

```text
A1 → A2
```

через объект/субъект и правила.

```text
A2 → A3
```

аналогично.

А уже спорные места отдать semantic verifier.

---

# 9. Для этого тебе очень пригодится Predicate Knowledge Base

То, о чём мы говорили в предыдущем сообщении.

Каждый predicate должен иметь свойства примерно:

```text
inhibits
    inverse = inhibitedBy
    produces_state = inhibited
    direction = causal
```

```text
increases
    inverse = decreases
    direction = causal
```

```text
supports
    direction = evidential
```

И можно задавать composition rules:

```text
inhibits + activation
    → inhibition

produces + causes
    → causes
```

Тогда большая часть inference становится обычным symbolic reasoning.

---

# 10. И это очень хорошо сочетается с твоей идеей автоматизированного учёного

Тогда роль LLM становится совсем другой.

Не:

```text
LLM:
"Посмотри на миллион утверждений и нарисуй граф."
```

а:

```text
Symbolic Engine
    ↓
строит кандидатов
    ↓
LLM
    ↓
проверяет неоднозначные случаи
    ↓
Symbolic Engine
    ↓
строит DAG
```

Это намного дешевле и, что ещё важнее, **гораздо более объяснимо**.

Для каждой стрелки можно хранить:

```text
A1 → A2

dependency_type = mechanistic

discovery_method = rule_17

verification = symbolic

confidence = 1.0
```

или:

```text
discovery_method = embedding

verification = LLM

confidence = 0.84
```

---

# 11. А позже LLM можно постепенно вообще вытеснять

Это одна из самых интересных перспектив.

Например первоначально:

```text
1000 candidate edges
↓
LLM проверяет 1000
```

Потом ты обнаруживаешь паттерны:

```text
90% этих решений LLM принимает по правилу X
```

И создаёшь:

```text
Rule X
```

После этого:

```text
1000
↓
900 symbolic
↓
100 ambiguous
↓
LLM
```

Потом:

```text
980 symbolic
↓
20 LLM
```

То есть система постепенно становится **дешевле и более формальной**, а LLM остаётся там, где действительно требуется семантическое понимание.

---

# 12. Но есть ещё более фундаментальный вопрос

Связь между блоками должна отвечать:

> **Почему этот блок нужен для следующего?**

И тут я бы не пытался вывести её исключительно из двух assertions.

Например:

```text
A1:
Rapamycin inhibits mTOR

A2:
mTOR inhibition increases autophagy

A3:
Autophagy reduces cellular damage
```

Связи:

```text
A1 → A2
A2 → A3
```

можно вывести из структуры.

Но если появится:

```text
A4:
Rapamycin increases lifespan
```

то для карты может быть связь:

```text
A3 → A4
```

только если существует некоторый механизм/доказательство, соединяющий cellular damage и lifespan.

Поэтому фактически ты ищешь **цепочки вывода**, а не просто связи.

---

# 13. И тогда задача становится похожей на поиск пути

Для цели `G`:

```text
find:
A1 → A2 → A3 → ... → G
```

где каждое ребро удовлетворяет:

```text
Dependency(Ai, Ai+1)
```

А затем можно искать:

```text
shortest path
highest confidence path
strongest evidence path
least uncertain path
multiple independent paths
```

И это уже очень похоже на то, что ты изначально хотел получить от Карты Знаний.

# 14. Поэтому мой ответ: **нет, дорогая нейросеть не обязательна**

Я бы строил систему в такой последовательности:

```text
                 ┌── exact matching
                 │
Assertions ──────┼── property matching
                 │
                 ├── predicate rules
                 │
                 ├── graph inference
                 │
                 └── embeddings
                         ↓
                  Candidate edges
                         ↓
                  Semantic verifier
                    ├── symbolic
                    └── LLM
                         ↓
                Dependency DAG
                         ↓
                    Visualization
```

И ключевой принцип:

> **Нейросеть должна не строить весь граф, а разрешать семантическую неопределённость, которую не удалось устранить формальными правилами.**

Это особенно хорошо подходит твоей идее **Knowledge Language + symbolic AI + neural AI**.

А ещё я бы вообще **не начинал сейчас с LLM**. Сначала формализовал бы `Dependency(A, B)` и сделал простой deterministic engine. На маленьком наборе из 100–1000 утверждений станет очень быстро видно, каких правил нам реально не хватает. Именно из этих дыр затем и получится спецификация Semantic Verifier.
