# Архитектура графа и работа с Neo4j

## Запрос

Напиши пример Neo4j запроса к такой структуре
```
Article
    │
    ├── содержит → Experiment1
    ├── содержит → Experiment2
    ├── содержит → Table1
    ├── содержит → Figure3
    ├── содержит → Dataset7
    └── содержит → Hypothesis4
```

где нам нужна статья которая содержит датасет и у неё нужно вывести первый эксперимент.

## Ответ

Предположим, модель данных выглядит так:

```text
(:Article)-[:CONTAINS]->(:Experiment)
(:Article)-[:CONTAINS]->(:Dataset)
(:Article)-[:CONTAINS]->(:Table)
(:Article)-[:CONTAINS]->(:Figure)
(:Article)-[:CONTAINS]->(:Hypothesis)
```

Тогда задача:

> Найти статьи, содержащие хотя бы один Dataset, и вывести первый Experiment.

в Cypher решается так:

```cypher
MATCH (a:Article)-[:CONTAINS]->(:Dataset)
MATCH (a)-[:CONTAINS]->(e:Experiment)
RETURN a, e
LIMIT 1
```

Но здесь есть проблема: `LIMIT 1` вернёт только **одну статью**, а не первый эксперимент для каждой статьи.

---

## Если нужен первый эксперимент каждой статьи

Лучше использовать `collect()`:

```cypher
MATCH (a:Article)-[:CONTAINS]->(:Dataset)
MATCH (a)-[:CONTAINS]->(e:Experiment)
WITH a, collect(e) AS experiments
RETURN
    a,
    experiments[0] AS firstExperiment
```

---

## Если порядок экспериментов важен

Тогда у эксперимента должно быть поле, например

```text
Experiment {
    order: 1
}
```

или

```text
Experiment {
    number: 1
}
```

Тогда запрос будет выглядеть так:

```cypher
MATCH (a:Article)-[:CONTAINS]->(:Dataset)
MATCH (a)-[:CONTAINS]->(e:Experiment)
WITH a, e
ORDER BY e.order
WITH a, collect(e)[0] AS firstExperiment
RETURN a, firstExperiment
```

---

## Если используется твоя модель триплетов

Допустим, в графе есть сущности:

```
Article
Experiment
```

а отношение `содержит` хранится как обычный триплет:

```
Statement
├── subject
├── predicate
└── object
```

то запрос станет значительно сложнее, например:

```cypher
MATCH (a)-[:IS_A]->(:Article)

MATCH (s1:Statement)-[:SUBJECT]->(a)
MATCH (s1)-[:PREDICATE]->(:Predicate {name: "содержит"})
MATCH (s1)-[:OBJECT]->(d)
MATCH (d)-[:IS_A]->(:Dataset)

MATCH (s2:Statement)-[:SUBJECT]->(a)
MATCH (s2)-[:PREDICATE]->(:Predicate {name: "содержит"})
MATCH (s2)-[:OBJECT]->(e)
MATCH (e)-[:IS_A]->(:Experiment)

RETURN a, e
LIMIT 1
```

---

## Я бы предложил для твоей архитектуры ещё одну оптимизацию

Ты собираешься хранить **все знания** в виде триплетов. Это очень гибко, но запросы вроде приведённого становятся длинными и требуют множества соединений (`MATCH`).

Поэтому я бы разделил два уровня:

* **Семантический уровень** — пользователь пишет триплеты (`Article → содержит → Experiment`).
* **Физический уровень Neo4j** — редактор автоматически компилирует их в обычные связи:

```text
(:Article)-[:CONTAINS]->(:Experiment)
```

а сами триплеты (`Statement`) хранятся только для случаев, когда нужны ссылки на утверждения, история изменений, источники или метаутверждения.

Тогда большинство запросов будут очень короткими и быстрыми:

```cypher
MATCH (a:Article)-[:CONTAINS]->(:Dataset)
MATCH (a)-[:CONTAINS]->(e:Experiment)
RETURN a, e
```

а при необходимости всегда можно обратиться к объектам `Statement`. Это позволит сохранить выразительность твоего языка и одновременно избежать усложнения запросов к графовой базе данных. На мой взгляд, это один из лучших компромиссов между удобством языка и производительностью Neo4j.


## Запрос

Как тогда обращаться к объектам Statement?

## Ответ

Вот здесь, на мой взгляд, находится ключевое архитектурное решение. Если у тебя есть **Statement** как отдельная сущность, то к нему нужно обращаться как к обычному узлу графа.

Например, модель может выглядеть так:

```text
(s:Statement {
    id: "fb3179ac-d59d-42f7-a2a9-363e15b029ad"
})

(a:Article {
    id: "8707def1-b77f-48b9-81ac-10d09f44a714"
})

(t:Type {
    name: "статья"
})

(s)-[:SUBJECT]->(a)
(s)-[:PREDICATE]->(:Predicate {name:"является"})
(s)-[:OBJECT]->(t)
```

Тогда найти Statement по UUID очень просто:

```cypher
MATCH (s:Statement {id: $statementId})
RETURN s
```

---

## Получить сам триплет

```cypher
MATCH (s:Statement {id:$statementId})
MATCH (s)-[:SUBJECT]->(subj)
MATCH (s)-[:PREDICATE]->(pred)
MATCH (s)-[:OBJECT]->(obj)

RETURN subj, pred, obj
```

---

## Добавить источник утверждения

```cypher
MATCH (s:Statement {id:$statementId})
MATCH (src:Article {id:$articleId})

CREATE (s)-[:SOURCE]->(src)
```

---

## Или уверенность

```cypher
MATCH (s:Statement {id:$statementId})

SET s.confidence = 0.93
```

# Но...

Если честно, я бы на этом месте остановился и подумал ещё раз над моделью хранения.

Потому что сейчас получается:

```text
Statement
    │
    ├── SUBJECT
    ├── PREDICATE
    └── OBJECT
```

То есть **каждый триплет превращается в четыре узла и три связи**.

Если у тебя 100 миллионов утверждений, то получится примерно:

* 100 млн узлов Statement;
* 300 млн служебных связей SUBJECT/PREDICATE/OBJECT.

Это огромный оверхед.

---

# Я бы предложил другой вариант

Хранить Statement так:

```text
(s:Statement {
    id: "...",
    subject: "...",
    predicate: "...",
    object: "...",
})
```

То есть SUBJECT/PREDICATE/OBJECT — это свойства узла Statement.

Тогда получить триплет:

```cypher
MATCH (s:Statement {id:$id})
RETURN s.subject, s.predicate, s.object
```

гораздо дешевле.

---

# А ещё лучше...

Если сущности уже существуют как узлы, то Statement вообще может быть **отношением Neo4j**.

Например:

```text
(a:Article)-[r:CONTAINS {
    id:"fb3179..."
}]->(e:Experiment)
```

То есть UUID хранится **на самой связи**.

Тогда запрос выглядит так:

```cypher
MATCH (a:Article)-[r:CONTAINS]->(e:Experiment)
WHERE r.id = $statementId
RETURN a, e, r
```

Именно это, кстати, ближе всего к тому, как Neo4j задумывался использоваться.

---

# Почему я изменил мнение?

Потому что теперь я вижу, что твой язык логически описывает **отношения между сущностями**.

Neo4j уже умеет хранить отношения.

Получается странно:

```text
Statement
    ↓
SUBJECT
    ↓
Article

Statement
    ↓
OBJECT
    ↓
Experiment
```

хотя можно сразу сделать

```text
Article
    ↓ CONTAINS
Experiment
```

и просто добавить UUID этой связи.

---

## В итоге я бы разделил два уровня

**Логический язык пользователя:**

```text
8707... → содержит → 3e6...
```

**Физическое хранение в Neo4j:**

```cypher
(a:Article)-[:CONTAINS {
    id: "55a0c4e1..."
}]->(e:Experiment)
```

Тогда:

* запросы остаются очень быстрыми;
* каждое утверждение по-прежнему имеет UUID;
* на него можно ссылаться по `r.id`;
* не нужно создавать отдельный узел `Statement` для каждого триплета.

## Но есть один нюанс, который нельзя игнорировать

Такой подход прекрасно работает для **обычных утверждений**, но **не работает напрямую для метаутверждений**.

Например:

```text
S1:
GeneA → активирует → GeneB

S2:
S1 → источник → Article1
```

Здесь `S1` становится **субъектом другого утверждения**. В Neo4j отношения (`Relationship`) не могут быть началом или концом других отношений — связи могут соединять только узлы.

Именно поэтому RDF придумал reification, а позже RDF-star.

Поэтому тебе нужно заранее решить один фундаментальный вопрос:

* Если **метаутверждения — ключевая часть языка** (а судя по твоим примерам, это так), то `Statement` почти наверняка должен быть **узлом**, иначе ты потеряешь возможность естественно строить граф утверждений об утверждениях.
* Если же метаутверждения будут редкими, можно хранить обычные утверждения как связи Neo4j, а при необходимости автоматически "поднимать" конкретную связь до объекта `Statement`.

Мне кажется, именно этот выбор — **"Statement как узел" против "Statement как связь"** — станет одним из самых важных архитектурных решений для всей "Карты Знаний".


## Запрос

метаутверждения — ключевая часть языка

## Ответ

Тогда, на мой взгляд, решение становится практически однозначным:

> **Statement должен быть узлом, а не связью Neo4j.**

И причина не в RDF или Neo4j, а в математике графов.

---

## Почему?

Потому что у тебя **утверждение — это объект предметной области**.

Например

```text
S1:
TP53 → ингибирует → mTOR
```

Это не просто связь.

У неё есть:

* источник;
* автор;
* дата;
* вероятность;
* p-value;
* доверительный интервал;
* метод;
* эксперимент;
* и самое главное — **на неё можно ссылаться**.

То есть

```text
S2:
S1 → подтверждено → Experiment17
```

или

```text
S3:
S1 → опровергнуто → Experiment24
```

или

```text
S4:
S1 → имеет p-value → 0.003
```

Получается, что **утверждение живёт собственной жизнью**.

## Я бы предложил ещё один шаг, который может сильно упростить архитектуру

Вместо того чтобы хранить отдельные узлы `Predicate` (`:Predicate {name: "ингибирует"}`), использовать **тип связи Neo4j** как материализованное представление предиката.

Например, одно утверждение:

```
Statement {
    id: S1,
    subject: TP53,
    predicate: "ингибирует",
    object: MTOR
}
```

автоматически порождает индексную связь:

```cypher
(TP53)-[:INHIBITS {statementId: "S1"}]->(MTOR)
```

Тогда:

* запросы по биологическим связям используют быстрые отношения Neo4j;
* любые метаутверждения (`S1 → источник → Article42`, `S1 → p-value → 0.003`) работают через узел `Statement`;
* связь Neo4j содержит `statementId`, поэтому из результата поиска можно мгновенно перейти к исходному утверждению и всем его метаданным.

Получается двухуровневая архитектура:

1. **Statement** — каноническое представление знания.
2. **Связи Neo4j** — автоматически поддерживаемый индекс для эффективных запросов.

Для языка, в котором метаутверждения являются центральной концепцией, это выглядит очень сильным компромиссом между выразительностью и производительностью.
